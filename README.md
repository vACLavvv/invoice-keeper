# Invoice Keeper

Production: **https://aezakeeper.ru/**. Развёртывание, изоляция, backups, TLS и откат: [docs/DEPLOYMENT.md](docs/DEPLOYMENT.md). Рабочая база теперь на VPS; локальные каналы отключены для защиты от дублей.

Разовые и регулярные платежи команды: панель на русском, отдельные периоды оплаты, история, просрочки и напоминания в Telegram, email, webhook и панели за 3 дня. RUB, USD и EUR считаются отдельно, без конвертации.

Стек: Python 3.12, FastAPI, SQLite (WAL), HTML/CSS/JavaScript без сборки. Фоновая проверка работает внутри процесса приложения; Redis, Celery, внешняя БД и Node.js для запуска не нужны. Swagger поставляется локально и не зависит от CDN.

## Структура и команды

- `backend/` — FastAPI, база, интеграции, Telegram-бот и Python-зависимости.
- `frontend/` — страницы, JavaScript, CSS, шрифты и локальные библиотеки.
- `tests/` — автоматические проверки; `scripts/` — инструменты разработки.
- `deploy/` — Dockerfile, production Compose, Nginx и systemd; `docs/` — документация.

Полная карта — [docs/STRUCTURE.md](docs/STRUCTURE.md). Команды выполняются из корня проекта: `make help`, `make run`, `make test`, `make package`. Для запуска без make используйте инструкции ниже.

## Быстрый локальный запуск

Нужен Python 3.12+ с `venv`. Команды выполняются в папке проекта. На Windows используйте `.venv\Scripts\python` вместо `.venv/bin/python`.

```sh
python3 -m venv .venv
.venv/bin/python -m pip install -r backend/requirements.txt
.venv/bin/python -m backend.app.bootstrap --demo
.venv/bin/python -m backend.app.run
```

Откройте **http://127.0.0.1:18080**. Логин администратора — `ADMIN_USERNAME`, пароль — `ADMIN_PASSWORD` в локальном `.env`. Bootstrap генерирует уникальные пароли; общедоступного стандартного пароля нет. Для обычного пользователя используйте `DEMO_USERNAME` / `DEMO_PASSWORD` из того же файла.

`--demo` добавляет 12 примеров: 8 регулярных и 4 разовых платежа в RUB/USD/EUR, включая оплаченные и просроченные. Разовые примеры — макеты страницы, интеграция CRM, аудит безопасности и завершённая настройка аналитики. Даты относительные. Повторный `--demo` сохраняет непустую базу без повторного наполнения.

Для существующей установки: сначала сделайте резервную копию, затем выполните `.venv/bin/python -m backend.app.bootstrap --more-examples`. Это добавляет только шесть новых примеров (четыре разовых и два регулярных), сохраняя все текущие записи. Повторный запуск не дублирует их.

Для пустой рабочей базы выполните `python -m backend.app.bootstrap` **без** `--demo`. Для собственного `.env` используйте `.env.example`: замените `ADMIN_PASSWORD` на случайный пароль длиной 12–128 символов. Bootstrap не перезаписывает `.env`. Переменные окружения имеют приоритет над файлом.

По умолчанию приложение слушает только `127.0.0.1`. Остановить его можно через Ctrl+C; данные останутся в `data/invoice-keeper.sqlite3`. Другой локальный порт: `python -m backend.app.run --port 18082`.

## Возможности

- Вход, выход, две роли, cookie-сессии. Администратор задаётся в `.env`; через панель его учётная запись не управляется.
- Администратор добавляет и прекращает регулярные платежи, создаёт, изменяет и удаляет обычных пользователей.
- Пользователь видит общий список, подтверждает/отменяет оплату конкретного периода, исправляет фактическую дату. Эти ограничения проверяются и в API.
- Обзор по месяцам, поиск, фильтры по валюте и статусу, календарь, история действий и журнал Telegram.
- Платёж архивируется мягко: существующие периоды и история сохраняются; новые периоды и напоминания прекращаются.
- SQLite сохраняет платежи, оплаты, пользователей, сессии, журнал, чеки, ссылки, персональные отметки прочтения и состояния всех каналов после перезапуска.

Рабочая панель вдохновлена сдержанной типографикой и иерархией [Apple](https://www.apple.com/): светлые поверхности, тонкие границы, синие кнопки. Есть полноценная тёмная тема; сохранённый выбор пользователя сохраняется, начальная тема — светлая. Локальный Inter и SVG не требуют CDN. Превью: [`docs/DESIGN.md`](docs/DESIGN.md); адаптивность: [`docs/DEVICES.md`](docs/DEVICES.md).

Разделы следуют рабочему процессу: **Обзор → К оплате → История**; календарь и бюджет помогают планировать, «Регулярные» управляют повторением. Обзор показывает срочные задачи, следующие сроки, план текущего месяца и недавние оплаты. «К оплате» по умолчанию содержит все открытые сроки, включая следующие месяцы; фильтры периода, типа, валюты и поиска сужают список. История включает оплаты и архив, фильтр месяца для оплат использует фактическую дату; календарь и финансовый план используют срок оплаты.

В форме «Добавить платёж» выберите один раз или ежемесячно. У разового платежа ровно один срок и необязательное описание работы. Его оплата, исправление даты, отмена, чеки, уведомления и аудит работают так же, как у отдельного месячного периода. Нового разового платежа в следующем месяце не возникает. Администратор может убрать его в архив из окна оплаты; история остаётся в «Истории». Из раздела «Регулярные» форма сразу предлагает ежемесячное повторение.

## Правила дат и сумм

`APP_TIMEZONE=Europe/Moscow` определяет текущую дату. Срок и фактическая дата — календарные даты `YYYY-MM-DD`. Оплата в день срока своевременна; просрочка начинается на следующий день. Для оплаченного периода число дней просрочки считается по фактической дате, для неоплаченного — по сегодняшней. Исправление фактической даты пересчитывает просрочку, срок остаётся прежним. Будущая фактическая дата не допускается. При отмене оплаты дата очищается.

Суммы хранятся целым числом копеек/центов; API передаёт их десятичными строками. У каждой валюты свои итоги. В summary `unpaid` включает просроченные суммы, `overdue` — часть `unpaid`, а `total = paid + unpaid`. Фильтрация итогов идёт по **сроку оплаты**, а не по дате фактического платежа. Архивные периоды входят в историю и итоги; `include_archived=false` исключает их.

Якорь повторения — день первой оплаты. Пример: **31 января → 28 февраля → 31 марта → 30 апреля**; в високосном феврале — 29-е. Оплата и просрочка не влияют на создание следующих периодов. Периоды создаются до конца следующего календарного месяца включительно, а при добавлении далёкого будущего платежа создаётся его первый период. Проверка выполняется при запуске, чтении списка и в фоне. Календарь и бюджет вычисляют более далёкие даты как прогноз без добавления записей в историю. При выборе будущего платежа в календаре создаётся только выбранный период; у него своя отметка оплаты.

## Telegram

В версии 3.2 бот поддерживает /start, /menu, /payments, /week, /overdue, /summary, /panel и /help. Можно открыть карточку и после подтверждения отметить один период оплаченным. Команды доступны только доверенным пользователям в заданном чате. Подробности и ограничения — [TELEGRAM.md](docs/TELEGRAM.md).

По умолчанию `TELEGRAM_ENABLED=false`: приложение не отправляет сообщения и не имитирует успешную отправку.

1. Создайте бота через официальный BotFather и добавьте его в нужный чат с правом отправки сообщений.
2. Узнайте числовой `chat_id` своего чата; для группы он обычно отрицательный. Токен не передавайте в переписках и не добавляйте в Git.
3. В локальном `.env` задайте `TELEGRAM_BOT_TOKEN`, `TELEGRAM_CHAT_ID`, `TELEGRAM_ENABLED=true`.
4. Перезапустите приложение. При необходимости создайте тестовый платёж со сроком через 1–3 дня.

Неоплаченный активный период попадает в отправку за 3 дня до срока; если добавлен позже — проверка запускается сразу после создания. Фон проверяет сроки каждые 60 секунд. Сообщение содержит название, сумму, валюту и срок. Оплаченные и архивные периоды не отправляются. В одном проходе отправляется не более 20 сообщений; оставшаяся очередь обрабатывается в следующих проходах.

**Защита от дублей:** у периода одна запись отправки с уникальным ключом. Перед сетевым запросом фиксируется `sending`. Успешный ответ сохраняет `sent` и `message_id`; повторной отправки не происходит даже после отмены оплаты или перезапуска. Два одновременно работающих обработчика используют транзакции SQLite для взаимного исключения.

Telegram `sendMessage` не имеет ключа идемпотентности. Если соединение оборвалось после возможной доставки, одновременно гарантировать повторную доставку и отсутствие дублей невозможно. Здесь выбран приоритет отсутствия дублей: таймаут/неоднозначный ответ переводит запись в `uncertain`, и автоматический повтор блокируется. После падения процесса зависший `sending` через 5 минут также становится `uncertain`. Проверьте чат и настройки по разделу **Журнал**; скрытых повторов нет. При невозможности установить соединение или явном ответе 429 разрешён отложенный повтор. Для повторного получения неопределённого напоминания автоматической кнопки нет — это осознанное ограничение.

Реальная доставка требует действительных токена, чата и доступа сервера к `api.telegram.org`; без них проверена логика с имитацией ответов API.

## Все дополнительные возможности

В версии 3.1 сохранены девять допов из кейса: календарь с итогами на дату по валютам, SMTP, подписанный webhook, дополнительные уведомления в панели/браузере, расширенный аудит, кнопка «Оплачено» в Telegram, план бюджета на месяц/год, чеки/ссылки для периода и адаптивный интерфейс.

### Оплата прямо в Telegram

При включённом Telegram `TELEGRAM_BUTTONS_ENABLED=true` добавляет кнопку «Оплачено». В личном чате подтверждать может владелец чата. Для группы задайте **числовые Telegram user_id**, разделённые запятыми, в `TELEGRAM_ALLOWED_USER_IDS`; без списка кнопок для группы нет. Это доверенные участники команды, которым владелец установки разрешает подтверждать оплаты независимо от веб-логина. Не добавляйте незнакомых пользователей.

Кнопка привязана к конкретному сообщению и периоду случайным непрозрачным токеном. Подтверждение ставит текущую дату приложения, не затрагивает следующие месяцы, записывает actor `telegram:<id>` в аудит. Повторное нажатие сохраняет уже заданную дату. Для исправления даты и отмены используйте панель. После оплаты/архивирования кнопка убирается, после отмены оплаты снова появляется при синхронизации (примерно раз в 36 секунд при активном polling).

Старые отправленные сообщения получают кнопку через редактирование разметки, не через повторную отправку. Бот получает нажатия через getUpdates; входящий порт, публичный URL и Telegram webhook не нужны. Используйте один процесс и отдельного бота для этого приложения. Если у бота уже установлен webhook другого сервиса, приложение его не удаляет и не запускает обработчик кнопок.

### Почта через SMTP

Параметры в `.env` (пример без реальных секретов):

```dotenv
SMTP_ENABLED=false
SMTP_HOST=smtp.yandex.ru
SMTP_PORT=465
SMTP_SECURITY=ssl
SMTP_USERNAME=your-login
SMTP_PASSWORD=
SMTP_FROM=your-login@yandex.ru
SMTP_TO=recipient@example.com
```

Поддерживаются `ssl` и `starttls`; проверка сертификатов обязательна, CA берутся из certifi. Режим `none` допускается только для локального тестового SMTP на loopback. Получатель — один адрес; для команды можно использовать свой почтовый список рассылки. Пароль приложения хранится только в приватном `.env`/окружении, никогда не попадает в API, журнал или архив.

Для Яндекса включите доступ почтовых клиентов и пароли приложений в настройках почты, создайте пароль приложения **«Почта»** именно для отправляющего ящика. Официальные параметры и шаги: [инструкция Яндекс Почты](https://yandex.ru/support/yandex-360/customers/mail/ru/mail-clients/others.html). Обычный пароль веб-входа вместо пароля приложения не используйте.

Проверить **одним** тестовым письмом, не включая фоновую рассылку:

```sh
.venv/bin/python scripts/test_smtp.py
```

После успешного теста задайте `SMTP_ENABLED=true` и перезапустите приложение. На странице «Каналы» видны адрес отправителя, получателя и безопасный статус; администратор может отправить тест. В «Журнале» есть отдельная запись доставки для каждого периода и канала. `sent` / «Принято SMTP» означает принятие сервером, а не гарантию попадания во «Входящие». Факт получения проверяйте у получателя. Локальные автоматические тесты используют настоящий SMTP-приёмник aiosmtpd, а не имитацию функции send.

Для уменьшения риска спама отправляйте с собственного ящика через официальный SMTP его провайдера согласованному получателю, сохраняйте корректный From и не делайте массовую рассылку. SPF/DKIM/DMARC для домена `yandex.ru` обслуживает провайдер; для собственного домена настройте аутентификацию у своего почтового сервиса. Гарантии обхода спам-фильтров нет. См. [рекомендации Gmail для отправителей](https://support.google.com/mail/answer/81126?hl=en).

### Webhook

```dotenv
WEBHOOK_ENABLED=false
WEBHOOK_URL=https://your-service.example/events
WEBHOOK_SECRET=replace-with-a-random-secret-at-least-24-characters
WEBHOOK_ALLOW_LOCALHOST=false
```

Генерация секрета: `.venv/bin/python -c "import secrets; print(secrets.token_urlsafe(32))"`. Сохраните его в приватном `.env`, согласуйте с принимающим сервисом, задайте реальный URL, включите канал и перезапустите приложение. Почтовый адрес не является URL webhook.

Тело запроса — JSON `{"event":"payment.due","event_id":"...","payment":{"occurrence_id":1,"recurring_payment_id":1,"title":"...","amount":"24.00","currency":"USD","due_date":"2026-10-26"}}`. Заголовки:

- `Idempotency-Key` совпадает с `event_id` и сохраняется для периода/канала.
- `X-Invoice-Timestamp` — Unix seconds.
- `X-Invoice-Signature` — `sha256=` + hex HMAC-SHA256 от **timestamp + точка + исходные байты тела**, ключ — WEBHOOK_SECRET.

Получатель проверяет подпись constant-time, свежесть времени (например, ±5 минут), запоминает event_id и отвечает 2xx. Перенаправления не выполняются. По умолчанию блокируются loopback, private, link-local и metadata адреса, включая DNS-ответы. TLS проверяется для исходного hostname; соединение идёт к проверенному IP, чтобы не допустить DNS rebinding. Query-параметры URL и секрет не выдаются в API или журнал ошибок.

Для локальной защиты без внешнего сервиса есть приёмник:

```sh
.venv/bin/python -m backend.app.webhook_demo
```

Он слушает **только 127.0.0.1:18083**, проверяет подпись и ключ доставки, сохраняет события в приватный `data/webhook-demo.jsonl`. Для этой демонстрации задайте `WEBHOOK_URL=http://127.0.0.1:18083/events`, `WEBHOOK_ALLOW_LOCALHOST=true`, одинаковый секрет, `WEBHOOK_ENABLED=true` и перезапустите приложение. Это локальный исходящий канал, никаких портов на VDS открывать не нужно.

Для защиты удобнее запустить оба процесса одной командой (отдельный приёмник предварительно остановите через его Ctrl+C):

```sh
.venv/bin/python -m backend.app.run --demo-webhook
```

Этот флаг включает локальный webhook только для текущего запуска, не переписывает `.env`. Секрет берётся из `.env`, создаваемого bootstrap. Приложение ждёт готовности приёмника и останавливает своего дочернего процесса при выходе. Если порт занят, чужой процесс не прерывается. Другой порт приёмника: `--webhook-port 18085`. В обычной конфигурации возвращайте `WEBHOOK_ALLOW_LOCALHOST=false`.

### Уведомления панели и браузера

`IN_APP_ENABLED=true` включает сохраняемые напоминания в разделе «Уведомления» и счётчик. Каждая учётная запись имеет свои отметки прочтения. Нажмите «Включить» для системных уведомлений браузера и дайте разрешение самостоятельно. Они работают только при открытой панели; это не фоновый Web Push. Разрешение можно отозвать в браузере, показы отключить той же кнопкой.

### Бюджет, календарь, чеки

«Бюджет» показывает план, оплачено и остаток отдельно для RUB, USD, EUR на выбранный месяц или год, включая корректные короткие месяцы и первый срок платежа. Прогноз строится по активным регулярным и разовым платежам (разовые учитываются только в свой единственный срок), по желанию — с уже сохранёнными архивными периодами. Будущие прогнозы не создают новые неоплаченные записи сами по себе.

«Календарь» показывает платежи и итог по каждой валюте на дату. Нажмите сумму дня для подробностей. Периоды за пределами уже созданной истории помечены `*` и создаются только при открытии их оплаты.

В окне оплаты можно добавить до **10 вложений**: PDF, PNG, JPEG, WebP до **5 MiB** или HTTP(S)-ссылку. Тип файла проверяется по сигнатуре, HTML/SVG не принимаются. Файлы выдаются как скачивание только после входа, хранятся в самой SQLite-базе и входят в её резервную копию. Вложение принадлежит конкретному периоду, не копируется на соседние месяцы. Удаление и добавление пишутся в аудит. В свежих демоданных есть демонстрационная ссылка на квитанцию.

### Обновление существующей базы

При запуске выполняется транзакционная идемпотентная миграция **v1/v2/v3 → v4**. Платежи, оплаты, пользователи и уже отправленные Telegram-сообщения сохраняются; известные отправки не повторяются. Перед первым обновлением выполните `scripts/backup.py`. База v4 сохраняет тип платежа и описание работы и добавляет журнал обработки команд Telegram с временными кнопками; для отката используйте отдельный бэкап, сделанный до обновления, не удаляйте таблицы вручную.

## API и Swagger

После входа откройте **http://127.0.0.1:18080/api/v1/docs**. Экспорт спецификации: [`docs/openapi.json`](docs/openapi.json); актуальная схема — `/api/v1/openapi.json`. Все данные и Swagger требуют авторизации.

Основные маршруты:

| Метод | Маршрут | Доступ |
|---|---|---|
| POST | `/api/v1/auth/login` | Вход |
| GET | `/api/v1/auth/me` | Авторизованные |
| POST | `/api/v1/auth/logout` | Авторизованные + CSRF |
| GET / POST | `/api/v1/recurring-payments` | Все / администратор |
| DELETE | `/api/v1/recurring-payments/{id}` | Администратор |
| GET / POST | `/api/v1/one-time-payments` | Все / администратор |
| DELETE | `/api/v1/one-time-payments/{id}` | Администратор; id периода |
| GET | `/api/v1/payment-occurrences` | Все |
| GET / PATCH | `/api/v1/payment-occurrences/{id}` | Все |
| GET | `/api/v1/payments/summary` | Все |
| GET / POST | `/api/v1/users` | Администратор |
| PATCH / DELETE | `/api/v1/users/{id}` | Администратор |
| GET | `/api/v1/docs` | Все |

Дополнительные маршруты под `/api/v1`: `/calendar`, `/payments/budget`, `/notifications`, `/deliveries`, `/integrations`, `/settings`, `/reminders`, `/audit-log`, `/audit-log/page`, `/system-logs`, `/payment-occurrences/{id}/attachments`, `/payment-occurrences/{id}/attachment-links`, `/attachments/{id}/download`. Полная схема и write-операции доступны в Swagger. `/healthz` возвращает только доступность приложения и базы.

В **Журнале** три вкладки: **Действия**, **Доставка** и **Системные логи**. Последняя показывает запросы/ошибки сервера Uvicorn, работу фоновых задач и локального webhook, с фильтрами, страницами и ротацией до 8 MiB. Доступ только у администратора; тела/заголовки запросов не пишутся, секреты маскируются. Каталог `data/logs` не входит в архив. Подробности: [docs/SYSTEM_LOGS.md](docs/SYSTEM_LOGS.md).

Администратор видит **Действия** с фильтрами по датам, пользователю, действию и тексту, страницами по 25 событий и подробностями «было → стало». История включает записи старше последних 100 и сохраняется после перезапуска. Удаление пользователя не удаляет его действия. Описание API и сценарий защиты: [docs/AUDIT.md](docs/AUDIT.md).

Авторизация использует cookie `invoice_session`. При входе и в `auth/me` возвращается `csrf_token`: передавайте его в **X-CSRF-Token** для всех изменяющих запросов, кроме login. Swagger UI 5.34.0 поддерживает OpenAPI 3.1, использует открытую cookie-сессию и автоматически подставляет актуальный CSRF-токен в изменяющие запросы. Токен вручную копировать не нужно; для собственного API-клиента заголовок по-прежнему обязателен. Внешние CDN и валидатор не используются; лицензии Swagger лежат рядом с локальными ресурсами. Cookie HttpOnly, SameSite=Strict; CSRF-токены в БД и URL не публикуются. Срок сессии — 12 часов. Смена пароля пользователя и его удаление отзывают все его сессии. Изменение admin-пароля в `.env` после перезапуска отзывает прежние админские сессии.

Примеры тела запроса:

Разовый: `POST /api/v1/one-time-payments` с `{"title":"Приёмка интеграции","amount":"380.00","currency":"EUR","due_date":"2026-11-03","notes":"После передачи исходников"}`. Ответ — один PaymentOccurrence; его `id` используется для оплаты, вложений и архивирования. `recurring_payment_id` — внутренний id определения, использовать его вместо id периода нельзя.

```json
{"title":"Облачный сервер", "amount":"24.00", "currency":"USD", "first_due_date":"2026-10-26", "frequency":"monthly"}
```

```json
{"paid":true, "paid_at":"2026-10-23"}
```

Исправление даты: `{"paid_at":"2026-10-22"}`. Отмена: `{"paid":false}` или `{"paid_at":null}`. Доступные фильтры списка: `from_date`, `to_date`, `status=paid|unpaid|overdue`, `currency=RUB|USD|EUR`, `search`, `include_archived`.

Тесты создают временные SQLite-базы и **не читают/не меняют** рабочую базу или VDS; Telegram заменён тестовой функцией; SMTP и webhook тестируются настоящими локальными приёмниками на случайных loopback-портах. Покрыты роли и API, CSRF, сессии, пользователи, конец месяца и високосный год, история и перезапуск, точные суммы, статусы, немедленное напоминание, отмена, отсутствие дублей, две конкурентные проверки и неоднозначная доставка.

## Защита приложения

Пароли обычных пользователей хешируются scrypt (N=32768, r=8, p=3, отдельная соль); старые хеши обновляются при успешном входе без смены пароля. Проверка учётных данных повторяется перед созданием сессии, чтобы удаление пользователя или смена пароля во время входа не открыли доступ. Повторный вход меняет cookie; на учётную запись допускается до 10 активных сессий. Работает ограничение попыток входа.

Проверяются Host, полный Origin и CSRF. Политика CSP запрещает inline-скрипты; для Swagger разрешены только встроенные стили. JSON-запрос ограничен 64 KiB, multipart — 5 MiB + 128 KiB; учитываются реальные байты, в том числе chunked, и время передачи (30 секунд). Загрузка авторизуется до разбора файла. Ошибки и логи скрывают известные секреты. Файлы SQLite/WAL/SHM получают права 600, новый каталог базы — 700. HTTPS-конфигурация добавляет HSTS.

Контроль целостности и упаковка защищают исходники для передачи, но не заменяют отдельную проверку целевого VDS. Подробности — в [`docs/ARCHITECTURE.md`](docs/ARCHITECTURE.md).

## Резервная копия

```sh
.venv/bin/python scripts/backup.py
```

Создаётся новый файл в `backups/` через SQLite online backup; копирование согласованно и при запущенном приложении. Скрипт проверяет `integrity_check`, не перезаписывает существующие файлы и не меняет исходную БД. Для восстановления остановите **только Invoice Keeper**, сохраните текущую БД с её WAL/SHM, затем восстановите копию в новый отдельный путь и задайте его в `DATABASE_PATH`. Бэкапы содержат пользовательские данные и хеши: храните их приватно.

## Docker: необязательный отдельный запуск

`compose.yaml` — необязательный локальный профиль. Production развёрнут отдельным `deploy/compose.prod.yaml`; конфигурация и результаты описаны в [DEPLOYMENT.md](docs/DEPLOYMENT.md). Не запускайте локальную копию с тем же Telegram-токеном и включёнными внешними каналами одновременно с VPS.

После создания `.env` можно выполнить:

```sh
docker compose up -d --build keeper
```

Адрес по умолчанию: **http://127.0.0.1:18081**. Имя Compose-проекта `invoice-keeper-hackathon`, данные — в отдельном именованном volume. Контейнер работает без root, с доступной для записи только `/data` и временной `/tmp`, лимитами CPU/памяти и логов. Локальная база `data/` не монтируется и диплом не затрагивается. Контейнерная база изначально пустая, демоданные в неё автоматически не копируются. Остановить только приложение: `docker compose stop keeper`.

Не используйте команды удаления volumes для остановки: они удаляют данные. Перед размещением на VDS сначала проверьте свободный порт и ресурсы и сделайте отдельный бэкап. Для публичного доступа нужен существующий HTTPS reverse proxy, `COOKIE_SECURE=true` и точный `PUBLIC_BASE_URL`, например `https://keeper.example.com` без пути. Его hostname разрешается автоматически; другие допустимые имена перечисляются в `APP_ALLOWED_HOSTS`. Приложение не доверяет произвольным X-Forwarded-*; Origin сравнивается с явно заданным публичным адресом. Конкретная интеграция в сервер требует отдельного выбора домена/маршрута. По умолчанию внешний доступ закрыт привязкой порта к loopback.

## Передача решения

```sh
.venv/bin/python scripts/package.py
.venv/bin/python scripts/verify_archive.py
```

Создаётся `output/invoice-keeper.zip` с исходниками, спецификацией, тестами и документацией. Упаковка использует явный список файлов; `.env`, рабочая БД, бэкапы, Git и `.venv` в архив не попадают. Тестовые данные воспроизводятся через bootstrap, реальные секреты получатель создаёт сам. Известные локальные секреты дополнительно проверяются по содержимому исходников: при обнаружении упаковка останавливается, предыдущий архив сохраняется. Внутри ZIP — `CHECKSUMS.sha256` для каждого файла; рядом — SHA-256 всего архива. `verify_archive.py` проверяет состав, CRC и хеши без распаковки или исполнения кода.
