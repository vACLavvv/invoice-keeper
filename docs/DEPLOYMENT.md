# Production: aezakeeper.ru

Развёртывание 24.10.2026. Приложение: **https://aezakeeper.ru/**. SSH — пользовательский алиас `vds` (`root@138.124.52.30`). Пароль администратора приложения сохранён; секреты в этой инструкции отсутствуют.

## Изоляция

- Отдельный проект Docker Compose `invoice-keeper-prod`, сеть `invoice-keeper-prod_default`, каталог `/opt/invoice-keeper` и контейнер `invoice-keeper-prod-keeper-1`.
- Backend опубликован только на `127.0.0.1:18081`. Локальный webhook слушает 18083 внутри контейнера и наружу не публикуется. Внешний доступ — через Nginx и HTTPS домена.
- Приложение работает от UID/GID 10001 без root, с read-only корнем, без Linux capabilities и с `no-new-privileges`. Запись разрешена в отдельный `/data` и ограниченный `/tmp`.
- Лимиты: 0.35 CPU, 384 MiB RAM, 64 PID; swap для контейнера отключён. Повышенный OOM score защищает соседние проекты при общем дефиците памяти.
- Сборка ограничена 384 MiB и 30% CPU. Python base image и официальный Certbot зафиксированы по OCI digest; runtime-зависимости — по версиям в requirements.txt.
- Для нового домена добавлен отдельный server block. В прежний nginx.conf добавлен **один include после существующего default server**. Конфигурация перед каждым reload проверена; Nginx обновлялся без перезапуска master-процесса. Другие виртуальные хосты сохранены.
- В Nginx есть ограничения запросов/соединений, отдельный лимит login и ограничение загрузки 6 MiB. Действуют Secure/HttpOnly/SameSite cookies, CSRF, проверка Host/Origin и CSP приложения.

## Данные и секреты

`/opt/invoice-keeper/config/runtime.env` — приватные настройки (root, 600), вне образа и вне исходников. `config/deploy.env` содержит только выбранный образ и пути. `/opt/invoice-keeper/data` принадлежит UID 10001, режим 700; SQLite, логи и JSONL приёмника — 600.

Для backup создан непривилегированный системный пользователь `invoice-keeper` (UID/GID 10001), без домашнего каталога и с nologin. Он имеет доступ только к данным и резервным копиям своего приложения; настройки и TLS-ключи остаются root-only. Backup использует SQLite online backup и открывает исходную базу в режиме ro. Права на каталог данных позволяют SQLite поддерживать WAL/SHM от того же UID, что и приложение.

Перенесены согласованный снимок SQLite, история системных логов и дедупликация локального webhook. Сохранены все 14 определений, 21 период, пользователь, вложение, 5 Telegram-отправок, 14 доставок и 35 прежних событий аудита; новые входы в production закономерно добавляются в аудит. Неопределённые отправки сохранены и не повторялись автоматически.

Локальный runner остановлен. В локальном `.env` Telegram/SMTP/webhook/in_app выключены, чтобы случайный локальный запуск не создал второй рабочий обработчик. Оригинальные локальные настройки и предмиграционная база сохранены приватно в `tmp/vps-cutover/`. Production использует собственную базу — локальные изменения больше не синхронизируются с VPS.

## Эксплуатация

После SSH-входа:

```sh
/opt/invoice-keeper/bin/keeper status
/opt/invoice-keeper/bin/keeper logs
/opt/invoice-keeper/bin/keeper backup
/opt/invoice-keeper/bin/keeper timers
```

`restart`, `stop` и `start` этого helper затрагивают только Invoice Keeper. Не применяйте глобальные `docker compose down` из других каталогов, `docker system prune` или удаление чужих volumes.

Веб-интерфейс: «Журнал → Действия / Доставка / Системные логи». Системные логи приложения/приёмника ограничены 8 MiB; Docker stdout — 5 MiB × 2. Отдельный error log Nginx проверяется logrotate каждые 15 минут при размере 5 MiB, сохраняются три ротации.

Системные таймеры:

- `invoice-keeper-backup.timer`: ежедневный согласованный backup; последние 7 копий, целевой общий бюджет 512 MiB, минимум 1 GiB свободного места перед созданием. Файлы в `/opt/invoice-keeper/backups`, 600. Посторонние файлы retention не удаляет.
- `invoice-keeper-cert-renew.timer`: проверка сертификата дважды в сутки. Используется отдельный Certbot с ограниченными ресурсами; Nginx reload выполняется только при изменении сертификата и после `nginx -t`. Проверено реальное тестовое продление (`--dry-run`).
- `invoice-keeper-logrotate.timer`: ротация только error log этого проекта.

Статус/ошибки jobs: `systemctl status invoice-keeper-backup.service invoice-keeper-cert-renew.service`; детали — `journalctl -u <имя.service>`. Эти jobs не входят в бессрочный бизнес-аудит приложения.

## Обновление и откат

Активный релиз — symlink `/opt/invoice-keeper/current`; исходники и image.json лежат в `releases/<release-id>`. До обновления создайте свежую копию БД, проверьте свободное место, соберите новый immutable tag и выполните staging acceptance на отдельной базе с отключёнными внешними каналами. Не включайте второй Telegram poller/SMTP worker с клоном рабочей базы.

После проверки изменяются только image/path этого Compose-проекта. До отката проверьте совместимость схемы: откатывать необходимо согласованную пару «образ + снимок данных», предварительно сохранив текущую production-базу. Не заменяйте живой SQLite-файл при работающем приложении и не удаляйте WAL/SHM вручную.

Для первого развёртывания сохранены baseline.json, оригинал nginx.conf и приватный начальный снимок. Восстановление shared Nginx выполняется с учётом последующих чужих изменений: убрать именно свой include/server block, проверить конфигурацию и выполнить graceful reload. Не перезаписывать чужие новые настройки старой копией.

## Проверки

118 автоматических тестов; контейнерная проверка на реальном Linux: auth, Secure cookie, публичный Origin, создание/оплата/архив разового платежа, оба потока логов, непривилегированный UID, read-only FS и cgroup-лимит. На реальной базе тестовые платежи не создавались.

Сравнение с baseline подтвердило неизменность ID, image, StartTime, RestartCount, mounts и портов всех 28 прежних контейнеров (порядок mounts нормализован). Сохранены PID Docker, Nginx master и code-server; конфигурации AEGIS не менялись. `/readyz` дипломного API и `/docs` predictor дают 200, HTTPS Invoice Keeper — 200. Старые failed jobs калибровки AEGIS имеют даты сентября и не изменялись.

После изменения фильтрации у провайдера повторно проверены SMTP 465 и 587: TLS, авторизация Яндекса и NOOP успешны. Писем при этой проверке не отправлялось. Входящие почтовые порты и собственный SMTP-сервер приложению не нужны; фактический результат доставки будущих уведомлений смотрите во вкладке «Доставка».
