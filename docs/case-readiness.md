# Соответствие кейсу Aeza: Invoice Keeper

Проверено по всем 18 страницам исходного кейса. Требования документа рассматриваются как предметная спецификация. Дополнительные инструменты эксплуатации — наша инженерная инициатива, а не скрытое обязательное условие кейса.

## Неочевидные вопросы, которые стоит объяснить жюри

- «Без дублей» при потере сетевого ответа — не повод повторять вслепую. `uncertain` требует проверки человеком. Строгое exactly-once с внешним API без его идемпотентного ключа гарантировать нельзя.
- Исправление даты оплаты не меняет срок; новый период не перезаписывает старый. Границы месяца считаются в едином `APP_TIMEZONE`, а не в часовом поясе браузера.
- «Осталось оплатить» — сумма обязательств по срокам за выбранный период минус отмеченное командой как оплаченное. План учитывает график и паузы; банковского баланса, проверки списаний и расчёта свободных средств здесь нет.
- Занятие задачи и проверка перед началом отправки сериализуются короткими транзакциями. Сеть работает без write-lock; ответ сохраняется по токену попытки. Оплата, удаление или отвязка после фиксации начала не могут отозвать уже начатый внешний запрос. Проверяются конкуренция, отмена до этой границы и устаревший ответ.
- Корзина сохраняется после перезагрузки и перезапуска. Восстановление всего платежа не возвращает периоды, которые удалили отдельно; прежние архив и пауза сохраняются. `sent` и `uncertain` не сбрасываются ради повторной отправки.
- Личные Telegram-напоминания `due`/`overdue` хранятся в `deliveries`: сохраняются попытки и `retry_after`, максимум 5 попыток для заведомо недоставленного. Отвязка/смена ответственного проверяется перед отправкой; старые личные отправки не повторяются при переходе на новую очередь.
- Название и состояние в журнале — текущий контекст, не исторический снимок. Подписанные события не меняются; неоднозначные старые ссылки на периоды после пауз не показываются, чтобы не приписать действие чужому платежу.
- SMTP-сервис остаётся внешним: имя отправителя `aezakeeper`, реальный адрес — адрес разрешённого SMTP-аккаунта. Пустой `SMTP_TO` выключает общую копию, не личные письма.
- Резервная копия без проверки восстановления и без ключа шифрования не доказывает восстановимость. Учебное восстановление выполняется отдельно от production.
- Prometheus/Grafana наблюдают планировщик и результаты доставки отдельно от HTTP health. Kubernetes на одной VPS не устраняет единую точку отказа и не требуется кейсом.

## Живая демонстрация (около 7 минут)

1. Показать закрытый API без входа, войти администратором.
2. Создать тестовый ежемесячный платёж со сроком через 2 дня. При настроенном и привязанном Telegram получить настоящее напоминание; иначе показать отключённый канал. Использовать понятное тестовое название, не настоящую оплату.
3. В боте открыть `/menu`, перейти в ближайшие, показать кнопку. Нажать «Оплачено» от привязанного аккаунта; повторное нажатие не создаст второй записи. Показать автора в журнале и независимый следующий период.
4. Войти обычным пользователем: сменить фактическую дату, снять/вернуть оплату; попытка админского API запрещена.
5. Показать просрочку, календарь с дневными/месячными итогами и годовой план в трёх валютах. Объяснить «Осталось оплатить» и ручные отметки; прикрепить чек к одному периоду.
6. Удалить этот период, перезагрузить страницу, открыть «История → Удалённые платежи», восстановить и проверить дату/чек. В журнале найти название платежа и срок, применить фильтры, открыть Swagger.
7. Если каналы и мониторинг подготовлены, показать фактическую доставку email/webhook, метрики и результат учебного восстановления. Объяснить ограничение одной VPS и состояние внешних резервных копий. Этот блок можно вынести в отдельный технический показ.

Не подменять живую проверку Telegram тестом с mock API: автоматические тесты доказывают логику, реальное нажатие дополнительно проверяет транспорт, аккаунт и конфигурацию.

Подробные кнопки и API для каждого шага — в [DEMO.md](DEMO.md). Наличие сценария не означает, что его уже прошли в браузере на текущей сборке.

## Историческая проверка на VPS 25 октября 2026

Ниже сохранён отчёт предыдущего выпуска. Он не подтверждает выпуск текущих изменений корзины, журнала, мобильного календаря и личной Telegram-очереди. SHA, результаты тестов и факт нового production-развёртывания нужно фиксировать после соответствующей проверки.

- Чистая исходная серверная версия `b09cba0` сверена с GitHub. В выпуск объединены также изменения расширения из `feature/extension-autodetect`.
- 119 Go-тестов прошли с `-race`; `go vet` прошёл. `govulncheck` не нашёл вызываемых уязвимостей (одна отмечена в неиспользуемой части зависимости).
- Новая сборка проверена на изолированной online-копии production: integrity и foreign keys OK, вход OK, 32 периода доступны, подписанный audit chain OK. Исходящие каналы отключены, сеть ограничена loopback.
- При первом выпуске все существующие бизнес-данные сохранились; схема осталась 7. Все пять AEGIS-контейнеров и PID общих сервисов сохранились.
- Пользователь привязал Telegram и нажал настоящую кнопку у отдельного тестового платежа: период `2026-10-27` оплачен `2026-10-25` от `admin`, следующий `2026-11-27` не оплачен. Ровно одна запись `occurrence.paid`; остальные исходные периоды не менялись.
- Prometheus получает `up=1`, Grafana запущена на loopback. Метрики без scrape-ключа возвращают 401. Мониторинг использовал около 122 MiB памяти на контрольном замере, без остановки дипломных сервисов.
- Локальный webhook-приёмник восстановлен отдельным systemd-сервисом: подписи HMAC обязательны, delivery ID согласуется с событием, повторы хранятся в SQLite inbox. Это демонстрационный потребитель, не внешний сервис.
- Защищённая копия БД вынесена с VPS на ноутбук; ключ шифрования сохранён отдельно с правами 0600. Регулярная автоматическая отправка бэкапов во внешнее хранилище пока не настроена.

MAX реализован и проверяется тестовым транспортом, но для живой отправки нужны действующий бот, числовой `MAX_CHAT_ID`, доступ сервера к API и при необходимости настроенный `MAX_CA_FILE`. Автотесты не подтверждают доступность аккаунта или транспорта. Операционные алерты вычисляются в Prometheus; их внешняя доставка в этом историческом отчёте не подключена.

Для текущих исправлений проверка календаря серверным рендером подтвердила дневные суммы трёх валют, отсутствие двойного учёта прогноза и месячный итог. Это не визуальная проверка: новый браузерный прогон не подтверждён из-за ограничения доступа инструмента к локальному адресу. Проверки типов и тесты API также не следует описывать как пройденный пользовательский сценарий в браузере.


## Дополнения: SSE, отчёты и измерения

Панель получает commit-сигналы через `/api/v1/events`: оплата из Telegram обновляет открытые данные без перезагрузки; при открытом диалоге обновление ждёт его закрытия. Reconnect восстанавливает состояние через API. Это поток одного процесса с ограничением подключений; он не обещает историю событий или распределённую доставку.

В Telegram `/report` и кнопка «Отчёт за месяц» строят PNG с планом, отмеченными оплатами и категориями; месяц и RUB/USD/EUR выбираются inline-кнопками. Расчёт общий с веб-бюджетом. Проверены авторизация, отвязка, пустой месяц, большие суммы, паузы, удаление/архив и изменение оплаты.

[Нагрузочный стенд и реальные результаты](load-testing.md): 10 000/50 000 расписаний, отдельная временная база, без реальных рассылок. Первый профиль выявил большие полные списки и удержание write-lock во время отправки. Теперь панель использует SQL-пагинацию и компактные сводки, материализация кэшируется, а сеть вынесена из write-транзакций. Старые полные API сохранены для совместимости; сравнение замеров и остающиеся ограничения приведены в отчёте. Это диагностический профиль, а не подтверждение production SLA. Часовые пояса проверены на границах суток и DST; календарные даты сохраняются как даты, моменты действий — в UTC.


Проверки следующего этапа: `pagination_test.go` сравнивает страницы с полным результатом, Unicode-поиск, историю по дате оплаты, материализацию через второе соединение и чтение при занятом writer; `calendar_view_test.go` проверяет полные итоги при ограниченных карточках. `delivery_concurrency_test.go` проверяет независимую запись во время заблокированного транспорта и владение попытками. Браузерные напоминания подключены на уровне всей панели; их жизненный цикл проверяет `npm run test:browser-notices`, последовательное обновление данных — `npm run test:async-load`. Эти проверки не заменяют реальный показ уведомления браузером и внешнюю доставку.
