# Нагрузочные проверки и часовые пояса

## Повторяемая локальная нагрузка

Из корня репозитория:

```sh
mkdir -p output
INVOICE_LOAD_SIZES=10000,50000 \
INVOICE_LOAD_OUTPUT="$PWD/output/load-profile.json" \
go test ./internal/app -run '^TestLoadProfile$' -count=1 -timeout=10m -v
```

Без `INVOICE_LOAD_SIZES` этот тест пропускается. Он создаёт отдельные временные SQLite-базы и HTTP-сервер на случайном loopback-порту. Рабочая `.env` не читается, production-база не открывается, Telegram/SMTP/webhook не вызываются. После завершения временные базы удаляются тестовым раннером. JSON-отчёт остаётся по указанному пути. Для быстрого прогона можно задать `INVOICE_LOAD_SIZES=1000`.

Каждый размер означает **число расписаний**, а не количество строк в базе. У расписаний месячный повтор с августа 2026 года; рабочая дата — 25 октября 2026 года. Создаются текущие, будущие и исторические периоды. Есть RUB/USD/EUR, пять категорий, оплаченная история, архивные и удалённые платежи, октябрьские паузы. Реальное число сохранённых и доступных периодов выводится отдельно.

Измеряются:

- Полный старый список, страницы периодов и расписаний, компактный обзор, календарь/страница дня, лента уведомлений, месячная сводка, годовой план и отметка оплаты: 12 запросов на операцию, одновременно три запроса. Время включает loopback HTTP и сериализацию ответа. Отчёт содержит p50/p95, максимум, ошибки, объём ответа и пропускную способность за измеренный интервал.
- Первая материализация периодов и шесть последовательных повторных проходов по уже материализованным расписаниям.
- Два прохода очереди Telegram с искусственной задержкой транспорта 20 мс: число отправок, оставшиеся ожидающие задачи, время первой/последней доставки и время конкурентной API-записи во время отправок.
- Начальный и выборочно измеренный максимальный Go heap, суммарные выделения памяти процесса теста. Это включает клиент и сервер в одном процессе, но не является измерением RSS production-процесса.
- Go/OS/архитектура, CPU/GOMAXPROCS, Git revision и список незакоммиченных файлов. Замеры изменённого рабочего дерева нельзя приписывать только указанному коммиту.

Это короткий диагностический профиль, а не подтверждение SLA или длительной устойчивости. p95 считается методом ближайшего ранга по 12 запросам, поэтому равен максимальному наблюдению этой выборки. Результат зависит от машины и фоновой нагрузки. Две пачки сообщений не доказывают срок обработки всего накопленного объёма. Искусственная задержка не моделирует лимиты Telegram и реальные сетевые ошибки; эти сценарии отдельно покрывают тесты транспорта и очереди.

Для честного сравнения «до/после» используйте одну машину, одинаковые размеры/параллелизм и версии Go, отдельные выходные файлы, одинаковый набор тестовых данных. Сначала изучите ошибки, размер ответа, блокировки записи и задержку очереди. Добавление Redis само по себе не заменяет эти измерения.

## Проверка часовых поясов

```sh
go test ./internal/app/config ./internal/app/schedule ./internal/app \
  -run 'TestAppTimezone|TestBusinessDate|TestConfiguredIANA|TestCivilDue|TestWorkspaceTimezone' -count=1
npm --prefix frontend run test:timezone
```

Backend-сценарии проверяют один UTC-момент в `UTC`, `Europe/Moscow`, `Europe/Berlin`, `Europe/Belgrade` и `Asia/Vladivostok`; даты около полуночи и обе границы летнего времени Berlin/Belgrade; високосный февраль и возврат к 31-му числу. API и Telegram должны выбирать одну рабочую дату из `APP_TIMEZONE`. Оплата в день срока считается своевременной, исправление фактической даты не меняет срок. Повторная Telegram-отметка сохраняет прежний момент изменения.

Срок и фактическая дата оплаты — календарные `YYYY-MM-DD`. `updated_at` — отдельный точный UTC timestamp внесения записи, проверяемый для API и Telegram. Такой подход сохраняет разницу между «оплатили вчера» и «сегодня внесли запись о вчерашней оплате». Набор браузерных зон в frontend-проверке проверяет форматирование данных через Node/Intl; это не визуальный прогон браузера.


## Результаты 25 октября 2026 года

[До оптимизации](load-profile-2026-10-25.json) и [после оптимизации](load-profile-optimized-2026-10-25.json): та же машина macOS arm64, Go 1.27.3, 10 логических CPU. Оба отчёта получены на незакоммиченном рабочем дереве; исходная ревизия и список изменений сохранены в JSON. HTTP-ошибок нет. В новом профиле дополнительно измеряются endpoint'ы пагинации, календаря, обзора и уведомлений. Это сравнение коротких локальных прогонов, не гарантия скорости VPS.

| Расписания / сохранённые периоды | Полный список p95, до → после | Сводка месяца p95, до → после | Запись оплаты p95, до → после | Пик Go heap, до → после |
|---|---:|---:|---:|---:|
| 10 000 / 39 500 | 1614 → 346 мс | 482 → 12 мс | 435 → 8 мс | 71 → 43 MiB |
| 50 000 / 197 500 | 4689 → 1438 мс | 2198 → 69 мс | 1936 → 20 мс | 436 → 173 MiB |

| Новый запрос, p95 | 10 000 расписаний | 50 000 расписаний | Объём ответа на 50 000 |
|---|---:|---:|---:|
| Страница платежей, 25 строк | 29 мс | 207 мс | 9,4 КБ |
| Дальняя страница платежей | 31 мс | 238 мс | 9,6 КБ |
| Страница расписаний | 2 мс | 6 мс | 10,1 КБ |
| Обзор с ограниченными очередями | 62 мс | 440 мс | 6,2 КБ |
| Календарь текущего месяца | 24 мс | 128 мс | 1,3 КБ |
| Календарь будущего месяца | 13 мс | 62 мс | 1,0 КБ |
| Страница платежей дня | 26 мс | 141 мс | 9,4 КБ |
| Уведомления, 50 строк + 100 свежих событий | 66 мс | 324 мс | 28,5 КБ |

На этом наборе все сроки приходятся на 28-е число: размер календаря особенно мал из-за трёх карточек на день. Для месяца с событиями каждый день верхняя граница предварительного списка — 93 карточки; остальные доступны через страницы дня. Итоги всегда включают все платежи, независимо от числа видимых карточек.

Старый полный JSON всё ещё занимает 14,79/74,24 MB (небольшой прирост из-за переносов строк). Он и CSV формируются построчно в приватном временном файле рядом с базой, затем отдаются клиенту; два одновременных экспорта ограничивают расход диска. Панель использует страницы и больше не загружает полный список. Пик heap относится ко всему тестовому процессу, включая клиент и все измеренные операции; это не RSS production-сервиса и не доказательство работы 50 000 расписаний в лимите контейнера 256 MiB.

Конкурентная API-запись во время искусственной отправки с задержкой 20 мс заняла **0,34/0,43 мс вместо 1244/2438 мс**. Два ограниченных `Tick` отправили по 40 сообщений; оставшийся backlog указан в JSON. Фоновый `Run` теперь продолжает полные пачки через 250 мс без повторной материализации, вместо ожидания полного интервала. Тест с 45 задачами отдельно проверяет такое продолжение. При 429 сохраняется пауза транспорта, которую наследуют новые задачи; автоматического повтора неопределённой отправки нет.

Годовой бюджет на 50 000 расписаний занял p95 499 мс против прежних 433 мс. Эта операция по-прежнему зависит от числа планов и не была ускорена пагинацией. Фильтры с точным количеством/суммами также зависят от объёма данных. Следующие измерения для роста — длительная нагрузка, RSS в реальном лимите VPS, несколько SSE-клиентов и фактические ограничения каналов. Подмена SQLite на Redis без этих замеров не подтверждает производительность.
