# Системные логи приложения и сервера

Версия 3.1, 24.10.2026. Откройте **Журнал → Системные логи** под администратором. Две соседние вкладки сохраняют бизнес-аудит («Действия») и состояния уведомлений («Доставка»).

## Что видно

- `invoice_keeper.service`: запуск/остановка сервиса, ошибка жизненного цикла.
- `uvicorn.error`: сообщения сервера Uvicorn, предупреждения и ошибки, traceback необработанных исключений.
- `invoice_keeper.http`: метод, путь, код ответа, длительность и случайный ID запроса. Ответы 4xx — WARNING, 5xx — ERROR, остальные — INFO.
- `invoice_keeper` / `invoice_keeper.delivery`: фоновые задачи, результаты отправок Telegram/SMTP/webhook/in_app, ошибки обработчиков и проверок каналов.
- `invoice_keeper.webhook`: отдельный процесс локального приёмника, запуск/остановка, проверка подписи, результаты HTTP-запросов.
- Предупреждения/ошибки Python-библиотек, которые они отправляют через стандартный logging. Уровень хранения — INFO и выше; отладочные дампы протоколов не включаются.

Есть фильтры по уровню, источнику, периоду и тексту. Время показано в APP_TIMEZONE, обычно Europe/Moscow. Порядок — новые сверху, 50 записей на странице; «Обновить» возвращает свежую первую страницу, сохраняя фильтры. Общий фоновый refresh панели обновляет первую страницу раз в минуту при открытой вкладке. Большие сообщения/traceback раскрываются по «Подробнее». Tab и стрелки переключают вкладки журнала.

Это логи **сервера приложения**, включая локальный приёмник. Системный журнал ОС, SSH, firewall, Docker daemon и другие приложения на VDS сюда не подключаются. Проект не получает дополнительных прав на компьютер или VDS.

## Хранение и защита

Логи собираются с включения версии 3.1. Старые сообщения терминала задним числом не восстанавливаются. Они переживают перезапуск отдельно от платежей и аудита:

- `<каталог базы>/logs/application.jsonl`: до 2 MiB, две резервные ротации (до 6 MiB).
- `<каталог базы>/logs/webhook.jsonl`: до 1 MiB, одна резервная ротация (до 2 MiB).
- Общий лимит — 8 MiB; старые файлы автоматически удаляются. В Docker этот каталог находится внутри существующего `/data`, на рабочем Mac — `data/logs`.
- Каталог 700, файлы 600. Чтение — только через API администратора. Каталог не раздаётся как static и не попадает в ZIP; API удаления/очистки логов нет.
- Логи HTTP не содержат тело запроса, заголовки, cookie и параметры URL. Успешное чтение самих системных логов, статика и health-check исключены из access-потока, чтобы просмотр не заполнял журнал.
- Известные пароли/токены интеграций и значения с чувствительными именами (`password`, `Authorization`, `invoice_session`, CSRF и т. п.) маскируются **до записи**; повторная маскировка применяется при чтении. Записи отображаются как экранированный текст, включая сообщения с HTML.
- Ошибка записи лога не прерывает HTTP-запросы/работу фоновых задач; во вкладке появляется предупреждение о недоступной части логов. Повреждённая или незавершённая строка пропускается. Произвольный путь к файлу через API передать нельзя, символические ссылки не читаются.

У бизнес-аудита отдельная история в SQLite: ротация системных логов не удаляет действия пользователей. Snapshot при перелистывании предотвращает сдвиг от новых записей; самые старые записи могут истечь при ротации. Это ограниченное диагностическое окно, не бессрочный архив.

## API и проверки

`GET /api/v1/system-logs` — администратор, обычный пользователь получает 403, без входа — 401. Параметры: `page`, `page_size` (1–100), `level`, `source`, `search`, `from_date`, `to_date`, `snapshot_id`. Контракт `SystemLogPage` включён в локальный Swagger/OpenAPI. Никаких операций с системной оболочкой через вкладку нет.

`tests/test_service_logs.py` проверяет роли, фильтры/страницы, московскую границу дня, HTTP-коды/длительности, traceback, скрытие секретов до файла и консоли, приватные права, ротацию, перезапуск, повреждённые строки и отказ записи. `tests/test_startup.py` запускает настоящие сервер/приёмник на временных loopback-портах и проверяет сбор логов обоих процессов, их корректную остановку.
