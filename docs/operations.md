# Эксплуатация и восстановление

## Выбор архитектуры

Go отдаёт встроенную статическую панель и выполняет фоновые задачи в одном процессе. SQLite WAL хранится на локальном диске. Для одной VPS и небольшой команды это уменьшает число точек отказа. Только один процесс должен опрашивать Telegram. Горизонтальное масштабирование требует отдельного проектирования воркера и хранения, а не запуска дополнительных копий бота.

Production работает как `invoice-keeper.service` за существующим nginx: `127.0.0.1:18081`. Данные — `/opt/invoice-keeper/data`, бинарник и приватный `.env` — `/opt/invoice-keeper/app`. Docker — проверяемый альтернативный способ запуска (`compose.yaml`), а не второй одновременно работающий экземпляр. Не запускайте Docker с production-токеном поверх systemd. Kubernetes не добавляет отказоустойчивости на единственной VPS; дополнительная сложность здесь не решает задачу кейса.

## Мониторинг

`METRICS_TOKEN` — отдельный случайный секрет длиной минимум 32 символа. Он даёт доступ только к `GET /api/v1/metrics` (совместимый алиас `/metrics`), не к API приложения. Пустое значение полностью выключает endpoint. Токен передаётся как `Authorization: Bearer …`, не в URL. В метриках нет названий платежей, email, логинов, URL, реквизитов и ID. Метрики HTTP имеют ограниченное число меток; проверки health/metrics исключены из пользовательского трафика.

В `deploy/monitoring` лежит отдельный Compose-проект: Prometheus (128 MiB, 0.15 CPU) и Grafana (192 MiB, 0.20 CPU), без Docker socket и доступа к базе приложения. Образы закреплены digest. Срок хранения — 7 дней, лимит блоков TSDB — 256 MB (WAL и служебные файлы требуют дополнительного места). Эти лимиты — потолки, не резервирование памяти.

Установка на сервере:

1. Скопировать `deploy/monitoring` в `/opt/invoice-keeper/monitoring`.
2. Создать `private/` с правами 0700. Записать в `private/metrics-token` тот же секрет, что в `METRICS_TOKEN` приложения. В `private/grafana-password` — отдельный случайный пароль. Файлы монтируются напрямую; внутри контейнера они должны читаться пользователем образа. Каталог родителя закрывает доступ другим пользователям VPS.
3. Перезапустить только `invoice-keeper.service`, затем `docker compose -f /opt/invoice-keeper/monitoring/compose.yaml up -d`.
4. Порты слушают только loopback: 19091 (Prometheus), 13001 (Grafana). Для просмотра: `ssh -L 13001:127.0.0.1:13001 -L 19091:127.0.0.1:19091 root@YOUR_VPS`. Открыть `http://localhost:13001`; логин `keeper`, пароль из приватного файла.

Панель `AezaKeeper · Operations`: доступность, возраст последнего успешного прохода планировщика, состояния очередей, частота/ошибки/задержки HTTP, Go heap, горутины и размер файла БД. Успешный проход планировщика не означает доставку всех писем: состояния `uncertain`/`failed` наблюдаются отдельно. Счётчики процесса обнуляются после рестарта; `rate()` учитывает сброс.

Правила Prometheus: недоступность, остановка планировщика, неоднозначные/неудачные отправки, доля HTTP 5xx. Они видны в Prometheus Alerts и на панели. Доставка этих операционных предупреждений во внешние каналы отдельно не настроена; это не следует путать с работающими платёжными напоминаниями.

Диагностика:

```sh
systemctl status invoice-keeper
journalctl -u invoice-keeper --since '-15 minutes'
curl -fsS http://127.0.0.1:18081/healthz
docker compose -f /opt/invoice-keeper/monitoring/compose.yaml ps
```

Не отправляйте заголовки авторизации и содержимое `.env` в логи или скриншоты. Если отправка `uncertain`, проверьте получение перед ручным повтором: запрос мог дойти, а ответ потеряться. При нагрузке мониторинг можно остановить отдельно: `docker compose ... stop`; бизнес-сервис продолжит работу. Дипломные сервисы AEGIS имеют свои порты и Compose-проект и не меняются.

## Резервная копия и проверка восстановления

Копия базы не заменяет копию `DATA_ENCRYPTION_KEY`: без ключа зашифрованные данные не восстановить. Храните `.env` и ключ отдельно, с правами 0600 и вне Git. Таймер `invoice-keeper-backup.timer` делает локальные online-копии; локальная копия не защищает от потери самой VPS. Для disaster recovery нужна отдельная защищённая копия вне VPS.

Из `/opt/invoice-keeper/app`, под пользователем сервиса:

```sh
./invoice-keeper backup --destination /opt/invoice-keeper/backups/manual.sqlite3
python3 scripts/verify-backup.py /opt/invoice-keeper/backups/manual.sqlite3
```

Скрипт проверяет целостность, внешние ключи и наличие таблиц в режиме read-only. Полная учебная проверка: скопировать backup в отдельный каталог, добавить приватный `.env` с тем же ключом шифрования и администратором, но **без** Telegram/MAX/SMTP/webhook и с `OFAC_ENABLED=false`, запустить на свободном loopback-порту. Проверить вход, список платежей и `/api/v1/audit-log/verify`. Ограничить исходящую сеть для учебного процесса. Production-базу не подменять для проверки.

При настоящем восстановлении: остановить только `invoice-keeper.service`; сохранить повреждённый набор БД/WAL/SHM; установить проверенную копию с владельцем `invoice-keeper`, правами 0600 и подходящим ключом; убедиться, что старые WAL/SHM не подмешиваются к копии; запустить совместимый бинарник и проверить health, вход и журнал. Восстановление старой базы может забыть уже отправленные уведомления — сверить очередь до включения каналов.

## Выпуск и откат

Собрать и проверить локально, до остановки production. Зафиксировать commit, SHA-256 бинарника, версию схемы, online-backup и приватную копию env. Проверить candidate на копии БД с отключёнными каналами. Перед заменой ещё раз сверить хеш текущего production-бинарника, чтобы не затереть параллельное обновление. Заменить бинарник атомарно, перезапустить только свой unit, проверить HTTPS, закрытость API и сохранность данных. Секреты из локального окружения на VPS не переносить.

Откат бинарника допустим, только если версия схемы совместима. Текущий выпуск обновляет schema 8 → 9: добавляет конечное состояние `failed` общей Telegram-очереди и атомарное хранение ответов идемпотентных операций. Существующие попытки и отметки начала отправки сохраняются. Бинарник schema 8 откажется открыть schema 9. Перед выпуском нужен проверенный на мигрированной копии совместимый recovery-бинарник; не понижайте `user_version` вручную и не восстанавливайте backup поверх новых пользовательских операций автоматически. Запишите, какие дополнительные сервисы временно остановлены, и верните их после демонстрации.

Очередь не держит write-транзакцию во время обращения к Telegram, SMTP, MAX или webhook. Короткие транзакции закрепляют задачу за попыткой, проверяют актуальность получателя и фиксируют результат. После фиксации начала внешней отправки отменить уже ушедший запрос невозможно. Оплата и удаление остаются доступны; пауза расписания, которая физически убирает затронутые периоды, возвращает 409, пока их отправка в работе. Повторить паузу можно после завершения отправки. Неопределённый результат не повторяется автоматически.

Полные старые `/payment-occurrences` и CSV-экспорт сериализуются построчно в приватный временный файл рядом с SQLite, не более двух ответов одновременно. Для экспорта нужны свободное место и права записи в каталог БД; `/tmp` контейнера увеличивать не требуется. При обычном завершении и отмене файл удаляется. После SIGKILL могут остаться файлы `.invoice-keeper-response-*`: удалять только после остановки приложения и проверки, что они не используются. Панель использует постраничные endpoint'ы и таких файлов не создаёт.

## Локальный webhook для демонстрации

`scripts/webhook_demo_receiver.py` — учебный потребитель на `127.0.0.1:18082/events`, unit — `deploy/invoice-keeper-webhook-demo.service`. Он проверяет HMAC-SHA256 тела и соответствие delivery ID событию/периоду; SQLite inbox отбрасывает повторы даже после перезапуска. Хранит только метаданные и SHA-256, без реквизитов и полного payload. Некорректная подпись получает 401. Это демонстрация доставки в другой процесс, не интеграция с внешней бухгалтерией.

Приватный `/opt/invoice-keeper/config/webhook-demo.env` содержит `WEBHOOK_SECRET` и `INBOX_DATABASE=/opt/invoice-keeper/data/webhook-demo/inbox.sqlite3`. Тот же секрет задаётся в `.env` приложения вместе с `WEBHOOK_URL=http://127.0.0.1:18082/events` и `WEBHOOK_ALLOW_PRIVATE=true`. Сервис не публикуется наружу. Подтверждение приёма: `journalctl -u invoice-keeper-webhook-demo`, результат отправки — «Журнал» → каналы в панели. Автоматические проверки протокола: `python3 -m unittest discover -s scripts -p 'test_*.py'`.

## Где открыть после обновления

| Сервис | Адрес | Доступ |
|---|---|---|
| Веб-панель | https://aezakeeper.ru | HTTPS, порт 443 |
| Ошибки доставки | https://aezakeeper.ru/notifications | Администратор, раздел «Ошибки отправки» |
| Аудит | https://aezakeeper.ru/activity | Администратор; проверка цепочки через `/api/v1/audit-log/verify` |
| Помощь | https://aezakeeper.ru/help | «Частые вопросы» раскрывается по нажатию |
| API приложения на сервере | `127.0.0.1:18081` | Только loopback, снаружи через HTTPS |
| Grafana | `127.0.0.1:13001` на сервере | SSH-туннель; логин `keeper` |
| Prometheus | `127.0.0.1:19091` на сервере | SSH-туннель |

На своём компьютере откройте терминал и оставьте эту команду работающей:

```sh
ssh -N -L 13001:127.0.0.1:13001 -L 19091:127.0.0.1:19091 root@138.124.52.30
```

Затем откройте **http://localhost:13001/d/keeper-finance** — «AezaKeeper · Финансы и доставка»; технический дашборд — **http://localhost:13001/d/keeper-operations**. Prometheus — **http://localhost:19091**. Пароль Grafana уже хранится на сервере; не копируйте его в Git:

```sh
ssh root@138.124.52.30 'cat /opt/invoice-keeper/monitoring/private/grafana-password'
```

Новый дашборд показывает число открытых/просроченных платежей, долг отдельно в RUB/USD/EUR, возраст воркера, ожидающие/неудачные/неопределённые доставки. Это суммы платежей, не баланс банковских счетов. Prometheus опрашивает приложение каждые 30 секунд. Нет смысла складывать задолженности разных валют без явной конвертации.

Telegram: `/menu` → «Ближайшие платежи» показывает один платёж и кнопки «Назад»/«Далее». `/menu` → «Отчёт за месяц» присылает график с выбором месяца и валюты.

Браузер: «Уведомления» → «Проверить». Тест ждёт принятия запроса service worker и показывает отдельную диагностику. Сайт не может проверить, отобразила ли ОС баннер; режим фокусирования и системные разрешения проверяются на устройстве. На iPhone для доступных системных уведомлений нужно открыть установленную на домашний экран веб-панель. Закрытая панель не опрашивает API: для неё продолжайте пользоваться Telegram/email. Это не Web Push-подписка.


## Консоль «Вебхук»

В боковом меню администратора откройте **Вебхук** (`/webhook`). Раздел выполняет один GET или POST по явному нажатию «Отправить запрос». Запрос отправляет сервер Invoice Keeper; ответ показывается как текст, без выполнения HTML/JavaScript. Это ручной конструктор запросов: настройки фоновой рассылки он не меняет.

- **Проверить приёмник** заполняет GET к `/healthz` настроенного локального приёмника. Затем нажмите «Отправить запрос»; ожидаемый ответ — HTTP 200 и `{"status":"ok"}`.
- **Тестовый POST** заполняет POST к настроенному webhook с событием `webhook.test`. Сервер подписывает его своим `WEBHOOK_SECRET`, а демонстрационный приёмник сохраняет в отдельной `test_inbox`, не затрагивая настоящие напоминания и платежи. Ответ — HTTP 200, `{"status":"accepted"}`.
- **Свой адрес** позволяет указать публичный HTTP(S) URL, GET/POST, заголовки и тело. POST может изменять данные получателя. Не отправляйте секреты стороннему адресу, которому не доверяете.

Консоль доступна только через сессию администратора и CSRF; API-токены не подходят. Служебные заголовки, cookie панели и сетевые proxy-переменные не пересылаются. Для своего адреса запрещены внутренние/loopback/metadata IP с проверкой при реальном подключении; редиректы не выполняются. Исключение для локального приёмника ограничено точным настроенным URL и его `/healthz`, только при `WEBHOOK_ALLOW_PRIVATE=true`. Адрес и секрет приёмника меняются через серверную конфигурацию.

Ограничения: 10 секунд, два параллельных запроса, тело до 64 KiB и отображаемый ответ до 128 KiB. Длинный ответ помечается как обрезанный. Автоматического повтора POST нет: после обрыва он мог выполниться на стороне получателя. Значения заголовков и тело не сохраняются в журнале/браузерном хранилище. В audit trail фиксируются начало и результат ручного обращения с безопасными метаданными.

API консоли: `GET /api/v1/webhook-console`, `POST /api/v1/webhook-console/requests`; контракт — в Swagger. На рабочем сервере приёмник остаётся `127.0.0.1:18082/events`, внешний порт для этой страницы открывать не нужно: https://aezakeeper.ru/webhook.
