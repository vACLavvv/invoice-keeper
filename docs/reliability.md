# Доставка и защищённый журнал

## Что именно гарантирует очередь

Напоминание сохраняется в SQLite до внешней отправки. Для одного периода, вида напоминания и получателя существует одна запись. Перезапуск сохраняет очередь, число попыток, паузу транспорта и конечный результат. Сетевой запрос выполняется вне write-транзакции: медленная доставка не блокирует оплату или создание платежей.

Короткие транзакции занимают задачу с уникальным `claim_token`, проверяют актуальность платежа/получателя, фиксируют начало отправки и затем результат. Чужая или устаревшая попытка не может перезаписать новую. До границы начала отправки оплата/отвязка отменяет задачу. Уже ушедший внешний запрос отозвать нельзя.

Telegram не предоставляет idempotency key для `sendMessage`. Поэтому абсолютную доставку «ровно один раз» при любом обрыве связи обещать нельзя. Система различает:

| Результат | Действие |
|---|---|
| Соединение заведомо не установлено; Telegram явно ответил `ok:false` с 429 или 5xx | Безопасный автоматический повтор |
| Telegram подтвердил отправку и вернул ID сообщения | `sent`, без повторов |
| Telegram явно отклонил запрос с постоянной ошибкой 4xx | `failed`, администратор видит ошибку |
| Таймаут после возможной отправки, потерянный/невалидный ответ, прерванная попытка после начала запроса | `uncertain`, автоматический повтор остановлен: сообщение могло дойти |

Семантика `ok` и минимального `retry_after` описана в [Telegram Bot API](https://core.telegram.org/bots/api#making-requests) и [ResponseParameters](https://core.telegram.org/bots/api#responseparameters). При 5xx без однозначного JSON-отказа результат остаётся неопределённым.

SMTP повторяется автоматически только при отказе до передачи DATA. Webhook сохраняет постоянный `X-Invoice-Keeper-Delivery`; получатель должен дедуплицировать этот ID. Его 429/5xx допускают повтор, поэтому обработчик webhook обязан сохранять ID принятого события. Пример такого получателя — `scripts/webhook_demo_receiver.py`.

## Политика повторов

Всего пять автоматических попыток. После подтверждённой неудачи задержка растёт экспоненциально с положительным случайным разбросом:

| Завершившаяся попытка | До следующей попытки |
|---|---|
| 1 | 60–75 секунд |
| 2 | 120–150 секунд |
| 3 | 240–300 секунд |
| 4 | 480–600 секунд |
| 5 | Статус `failed`, дальнейших автоматических попыток нет |

Это минимумы локальной политики. Если транспорт требует более долгую паузу (`retry_after` Telegram, безопасный повтор SMTP/webhook), используется больший срок. Фоновый планировщик подбирает задачу после этого срока, поэтому фактическая задержка может быть больше на интервал проверки. Пауза сохраняется в БД и распространяется на новые задачи того же транспорта. Для Telegram она действует на весь бот: API не объясняет, относится ли ограничение к одному чату или ко всем запросам. Полные готовые пачки продолжаются через 250 мс без повторного обхода всех расписаний.

## Очередь ошибок в панели

Администратор открывает **Уведомления → Ошибки отправки**. `GET /api/v1/delivery-failures` объединяет окончательные ошибки и неопределённые результаты Telegram, личных/дополнительных каналов и подтверждений email; список постраничный. Пользователь без прав администратора не получает доступ.

Повтор разрешён только для `failed`, если платёж ещё не оплачен/удалён/архивирован, канал включён и получатель по-прежнему соответствует назначению. `POST /api/v1/delivery-failures/retry` принимает очередь, ID периода, вид/канал доставки и `failure_token` из списка. Токен относится к конкретной ошибке: старый экран или двойное нажатие не может повторно запустить следующую попытку. Обновление очереди и запись `delivery.retry` в журнал выполняются в одной транзакции. Сохранённый лимит частоты при ручном повторе не обходится.

Для `uncertain` кнопки повтора нет. Сначала нужно проверить получение у адресата. Письмо подтверждения почты повторно запрашивается через существующий экран пользователя: создаётся новая ссылка, старый секрет не извлекается из очереди.

## Аудит

Изменения платежей и ручной повтор доставки записываются вместе с бизнес-операцией. Записи образуют HMAC-цепочку; отдельный `audit_head` обнаруживает удаление конца журнала. `GET /api/v1/audit-log/verify` проверяет цепочку и показывает место нарушения. Обычные пользователи не читают административный журнал и не могут удалять или редактировать его через API; таких методов API нет.

Это защита от незаметного редактирования, а не внешнее неизменяемое хранилище: владелец сервера с доступом к БД и ключу теоретически может пересоздать подписи. Для независимого доказательства нужен внешний архив/подписанный якорь. Тесты проверяют изменение записи, удаление хвоста, отсутствие API редактирования и атомарность записи о ручном повторе.

## Миграция

Схема 9 расширяет допустимые состояния общей Telegram-очереди значением `failed` и добавляет таблицу идемпотентных API-операций. Расширение `CHECK` выполняется в общей транзакции и сохраняет attempts, сроки, владение попыткой и отметку начала отправки. Миграция ничего не переотправляет. Старый бинарник со схемой 8 не открывает схему 9; для отката нужен совместимый бинарник, проверенный на копии базы. Живую базу нельзя автоматически подменять старым backup, иначе будут потеряны новые операции и защита от повторных уведомлений.

## Идемпотентность HTTP API

Для создания, изменения, оплаты, архивации, паузы, удаления и восстановления платежей поддерживается `X-Idempotency-Key` (8–128 символов `A–Z a–z 0–9 . _ : -`). Полный список операций есть в OpenAPI. Ключ относится к одному действию, аккаунту и текущим учётным данным, сохраняется **24 часа**. Одновременно с изменением и audit-записью сохраняются код и тело успешного ответа. Ошибка транзакции откатывает всё; отдельного промежутка между сохранением платежа и кэша нет.

Повтор того же метода/пути/тела возвращает исходный ответ с `X-Idempotency-Replayed: true`, даже если состояние платежа позже изменилось. Порядок JSON-полей и пробелы не важны. Другое тело или другой путь с тем же ключом возвращает `409 idempotency_conflict`. Авторизация, права записи и CSRF проверяются при каждом повторе; сохранённый ответ не является обходом доступа. Тело результата шифруется при включённом `DATA_ENCRYPTION_KEY`; добавление ключа позже шифрует и прежние ответы.

Панель создаёт ключ автоматически, объединяет одновременные одинаковые запросы внутри вкладки и сохраняет ключ в sessionStorage после сетевой ошибки/5xx/повреждённого успешного ответа. Повтор после перезагрузки этой вкладки в той же сессии использует прежний ключ. После подтверждённого успеха намеренное новое действие получает новый ключ. Это не координация между независимыми вкладками и не защита запросов клиента, который каждый раз присылает новый ключ. После 24 часов ключ может быть использован заново; для сомнительного давнего результата сначала проверьте наличие платежа.

Пример для клиента с write-токеном (настоящий токен подставляется локально):

```sh
curl https://aezakeeper.ru/api/v1/recurring-payments \
  -H 'Authorization: Bearer YOUR_WRITE_TOKEN' \
  -H 'Content-Type: application/json' \
  -H 'X-Idempotency-Key: 04ea811f-c2ce-46be-85c1-91cb214fc3a8' \
  --data '{"title":"Продление домена","amount":"1500.00","currency":"RUB","first_due_date":"2026-12-01","frequency":"yearly"}'
```

Это защищает записи о платежах и отметки оплаты от повторного выполнения. Invoice Keeper не выполняет списания с банковского счёта.

Для webhook адреса управляются в панели и имеют отдельные записи `webhook_endpoints`, очереди `webhook:<id>` и backoff. Два сетевых слота распределяются между адресами с ограничением одного активного запроса на адрес. Отключённый адрес не создаёт новых задач; начатая отправка завершается со своим исходным снимком адреса/секрета. Миграция старого канала сохраняет состояния и не рассылает уже подтверждённые события повторно. История доступна у получателя, а failed/uncertain также видны в общей панели ошибок.
