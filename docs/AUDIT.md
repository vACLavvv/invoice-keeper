# Журнал действий

Администратор открывает **Журнал → Действия**. Рядом есть отдельные вкладки **Доставка** (Telegram и дополнительные каналы) и **Системные логи** (сервер, запросы, ошибки, фоновые задачи). Описание диагностики: [SYSTEM_LOGS.md](SYSTEM_LOGS.md).

## Что сохраняется

Вход, неудачный вход, выход, отказы в администраторском доступе, создание и архивирование платежей, оплата и исправление даты, операции с пользователями и вложениями, тестирование каналов. Автор и событие записываются сервером. Изменение платежа и запись аудита выполняются в одной транзакции: ошибка записи аудита отменяет изменение.

Новые записи о платежах содержат название и срок. Для оплаты сохраняются старая и новая фактические даты, источник (панель/API или Telegram). Для пользователя — логин/имя до и после изменения; изменение пароля отражается только флагом. Удаление пользователя не удаляет его старые действия. Исторические записи, созданные до этого обновления, показываются с теми подробностями, которые были сохранены тогда.

Журнал хранится в SQLite и переживает перезапуск. Читать его могут только администраторы; API изменения или удаления записей нет. Пароли, cookie и CSRF-токены в записи аудита не передаются. Неудачный вход показывает введённый логин с пометкой «Логин не подтверждён».

## Поиск и страницы

- Фильтры: начальная и конечная дата, пользователь, действие, текстовый поиск. Нажмите **Применить**. Все условия действуют одновременно.
- Даты включают весь выбранный день в `APP_TIMEZONE`; в интерфейсе указан этот часовой пояс. В БД время хранится в UTC.
- Поиск учитывает кириллицу без различия регистра, названия событий, пользователя, объект и сохранённые подробности. Кавычки и `%` обрабатываются как обычные символы.
- Страница содержит 25 событий, новые сверху. На сервере фильтрация происходит до пагинации; можно просмотреть историю старше последних 100 записей.
- При переходе по страницам сохраняется верхняя граница ID: события, добавленные параллельно, не вызывают пропусков и повторений. **Обновить** возвращает первую страницу с актуальными событиями, сохраняя применённые фильтры. Первая страница также обновляется при обычном фоновом обновлении панели.
- **Сбросить** очищает фильтры. Ошибка загрузки показывается отдельно, предыдущий список не выдаётся за обновлённый.

## API

`GET /api/v1/audit-log/page` — только администратор. Параметры: `page` (от 1), `page_size` (1–100, по умолчанию 25), `from_date`, `to_date`, `actor`, `action`, `search`, `snapshot_id`.

Ответ содержит `items`, `total`, `page`, `page_size`, `pages`, `snapshot_id`, `timezone`, `actors`, `actions`. Для перехода на следующую страницу передайте полученный `snapshot_id`. Для новой выборки или обновления не передавайте его. Списки пользователей и действий строятся по сохранённой истории, включая удалённых пользователей.

Прежний `GET /api/v1/audit-log` сохраняет совместимость: список последних 100 записей. Новый API и схема ответа доступны в Swagger.

## Сценарий защиты

1. Создайте демонстрационный платёж и обычного пользователя.
2. Войдите этим пользователем и отметьте период оплаченным. Исправьте фактическую дату на другую допустимую дату.
3. Войдите администратором, откройте **Журнал**, выберите пользователя и нажмите **Применить**.
4. Покажите автора, время, название платежа, срок и «Дата оплаты: было → стало». Поиск «исправлена дата» оставит события исправления даты.
5. Попробуйте вход с неверным паролем. После успешного входа покажите событие «Неудачный вход» и результат «Ошибка входа».
6. Перезапустите приложение и убедитесь, что история сохранена. Обычному пользователю журнал недоступен.

Проверки: `python -m pytest -q tests/test_audit.py`. Используются временные базы и отключённые внешние отправки. Проверены границы дня, стабильные страницы при новых событиях, совместные фильтры, права, перезапуск, старые записи и откат операции при ошибке аудита.
