# Эксплуатация и восстановление

## Выбор архитектуры

Go отдаёт встроенную статическую панель и выполняет фоновые задачи в одном процессе. SQLite WAL хранится на локальном диске. Для одной VPS и небольшой команды это уменьшает число точек отказа. Только один процесс должен опрашивать Telegram. Горизонтальное масштабирование требует отдельного проектирования воркера и хранения, а не запуска дополнительных копий бота.

Production работает как `invoice-keeper.service` за существующим nginx: `127.0.0.1:18081`. Данные — `/opt/invoice-keeper/data`, бинарник и приватный `.env` — `/opt/invoice-keeper/app`. Docker — проверяемый альтернативный способ запуска (`compose.yaml`), а не второй одновременно работающий экземпляр. Не запускайте Docker с production-токеном поверх systemd. Kubernetes не добавляет отказоустойчивости на единственной VPS; дополнительная сложность здесь не решает задачу кейса.

## Мониторинг

`METRICS_TOKEN` — отдельный случайный секрет длиной минимум 32 символа. Он даёт доступ только к `GET /metrics`, не к API приложения. Пустое значение полностью выключает endpoint. Токен передаётся как `Authorization: Bearer …`, не в URL. В метриках нет названий платежей, email, логинов, URL, реквизитов и ID. Метрики HTTP имеют ограниченное число меток; проверки health/metrics исключены из пользовательского трафика.

В `deploy/monitoring` лежит отдельный Compose-проект: Prometheus (128 MiB, 0.15 CPU) и Grafana (192 MiB, 0.20 CPU), без Docker socket и доступа к базе приложения. Образы закреплены digest. Срок хранения — 7 дней, лимит блоков TSDB — 256 MB (WAL и служебные файлы требуют дополнительного места). Эти лимиты — потолки, не резервирование памяти.

Установка на сервере:

1. Скопировать `deploy/monitoring` в `/opt/invoice-keeper/monitoring`.
2. Создать `private/` с правами 0700. Записать в `private/metrics-token` тот же секрет, что в `METRICS_TOKEN` приложения. В `private/grafana-password` — отдельный случайный пароль. Файлы монтируются напрямую; внутри контейнера они должны читаться пользователем образа. Каталог родителя закрывает доступ другим пользователям VPS.
3. Перезапустить только `invoice-keeper.service`, затем `docker compose -f /opt/invoice-keeper/monitoring/compose.yaml up -d`.
4. Порты слушают только loopback: 19091 (Prometheus), 13001 (Grafana). Для просмотра: `ssh -L 13001:127.0.0.1:13001 -L 19091:127.0.0.1:19091 root@YOUR_VPS`. Открыть `http://localhost:13001`; логин `keeper`, пароль из приватного файла.

Панель `AezaKeeper · Operations`: доступность, возраст последнего успешного прохода планировщика, состояния очередей, частота/ошибки/задержки HTTP, Go heap, горутины и размер файла БД. Успешный проход планировщика не означает доставку всех писем: состояния `uncertain`/`failed` наблюдаются отдельно. Счётчики процесса обнуляются после рестарта; `rate()` учитывает сброс.

Правила Prometheus: недоступность, остановка планировщика, неоднозначные/неудачные отправки, доля HTTP 5xx. Они видны в Prometheus Alerts и на панели. Доставка этих операционных предупреждений во внешние каналы отдельно не настроена; это не следует путать с работающими платёжными напоминаниями.

Диагностика:

```sh
systemctl status invoice-keeper
journalctl -u invoice-keeper --since '-15 minutes'
curl -fsS http://127.0.0.1:18081/healthz
docker compose -f /opt/invoice-keeper/monitoring/compose.yaml ps
```

Не отправляйте заголовки авторизации и содержимое `.env` в логи или скриншоты. Если отправка `uncertain`, проверьте получение перед ручным повтором: запрос мог дойти, а ответ потеряться. При нагрузке мониторинг можно остановить отдельно: `docker compose ... stop`; бизнес-сервис продолжит работу. Дипломные сервисы AEGIS имеют свои порты и Compose-проект и не меняются.

## Резервная копия и проверка восстановления

Копия базы не заменяет копию `DATA_ENCRYPTION_KEY`: без ключа зашифрованные данные не восстановить. Храните `.env` и ключ отдельно, с правами 0600 и вне Git. Таймер `invoice-keeper-backup.timer` делает локальные online-копии; локальная копия не защищает от потери самой VPS. Для disaster recovery нужна отдельная защищённая копия вне VPS.

Из `/opt/invoice-keeper/app`, под пользователем сервиса:

```sh
./invoice-keeper backup --destination /opt/invoice-keeper/backups/manual.sqlite3
python3 scripts/verify-backup.py /opt/invoice-keeper/backups/manual.sqlite3
```

Скрипт проверяет целостность, внешние ключи и наличие таблиц в режиме read-only. Полная учебная проверка: скопировать backup в отдельный каталог, добавить приватный `.env` с тем же ключом шифрования и администратором, но **без** Telegram/MAX/SMTP/webhook и с `OFAC_ENABLED=false`, запустить на свободном loopback-порту. Проверить вход, список платежей и `/api/v1/audit-log/verify`. Ограничить исходящую сеть для учебного процесса. Production-базу не подменять для проверки.

При настоящем восстановлении: остановить только `invoice-keeper.service`; сохранить повреждённый набор БД/WAL/SHM; установить проверенную копию с владельцем `invoice-keeper`, правами 0600 и подходящим ключом; убедиться, что старые WAL/SHM не подмешиваются к копии; запустить совместимый бинарник и проверить health, вход и журнал. Восстановление старой базы может забыть уже отправленные уведомления — сверить очередь до включения каналов.

## Выпуск и откат

Собрать и проверить локально, до остановки production. Зафиксировать commit, SHA-256 бинарника, версию схемы, online-backup и приватную копию env. Проверить candidate на копии БД с отключёнными каналами. Перед заменой ещё раз сверить хеш текущего production-бинарника, чтобы не затереть параллельное обновление. Заменить бинарник атомарно, перезапустить только свой unit, проверить HTTPS, закрытость API и сохранность данных. Секреты из локального окружения на VPS не переносить.

Откат бинарника допустим, только если версия схемы совместима. В этом выпуске миграций БД нет (schema 7). Не восстанавливайте backup поверх новых пользовательских операций автоматически. Запишите, какие дополнительные сервисы временно остановлены, и верните их после демонстрации.
