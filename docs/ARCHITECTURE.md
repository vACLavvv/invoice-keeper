# Устройство и ограничения

Карта каталогов и точки запуска: [STRUCTURE.md](STRUCTURE.md).

## Поток данных

```text
Browser → FastAPI (auth + role + CSRF) → SQLite
                       │                   │
                       │             recurring_payments
                       │                   ↓ materialize
                       │             payment_occurrences
                       │                   ↓ unpaid, due ≤ today+3
                       └→ background worker → reminders → Telegram
```

`backend/app/config.py`: настройки из корневого `.env` и окружения. `backend/app/db.py`: схема v4 и короткие транзакции, `foreign_keys`, WAL, busy_timeout. Неизвестная версия базы останавливает запуск без изменения таблиц.

`backend/app/domain.py`: календарные правила, материализация периодов, вычисление статуса и просрочки, Decimal-форматирование. Уникальность `(recurring_payment_id, due_date)` не позволяет дублировать период при одновременных чтениях.

`backend/app/main.py`: маршруты, схемы, серверные ограничения, cookie-сессии и операции. При создании платежа и изменении оплаты сразу запускается фоновая проверка. Контрольные часы можно подменить только при создании приложения в Python-тестах; API для смены сегодняшней даты нет.

`backend/app/reminders.py`: периодический daemon-поток, снимаемая локальная блокировка и транзакционное занятие записи. После фиксации `sending` в короткой транзакции повторно проверяется активность и оплата. Сетевой запрос выполняется без write-lock SQLite, результат сохраняется отдельной транзакцией: медленный SMTP/Telegram не блокирует вход и панель. Уже начатую внешнюю отправку нельзя отозвать при одновременном изменении оплаты; все ещё не начатые попытки оплаченного/архивного периода отменяются. Пакет обрабатывается по одному сообщению.

При падении после доставки, но до записи результата, остаётся `sending`. Через 5 минут запись становится `uncertain`; повторной отправки нет. Снятие отметки оплаты не сбрасывает `sent`. Только заведомо недоставленные попытки (ConnectError и явный 429) повторяются автоматически. Журнал отдаёт безопасное описание ошибки; URL с токеном и исходный ответ Telegram не сохраняются.

## Авторизация

Пароли: scrypt N=32768, r=8, p=3 с индивидуальной случайной солью, не более двух параллельных вычислений (ограничение памяти). Старый формат N=16384, r=8, p=1 проверяется и обновляется при успешном входе. Формат хеша содержит параметры. После вычисления пароля запись пользователя повторно проверяется под write-транзакцией: смена пароля, логина или удаление во время входа не создают устаревшую сессию. Администратор определяется окружением и не хранится в `users`. Отпечаток текущих admin-настроек привязан к его сессии, поэтому смена пароля после рестарта отзывает старую сессию.

Повторный вход отзывает предыдущую cookie этого браузера; на учётную запись хранится не более 10 активных сессий, истёкшие очищаются. Случайный session token содержит 32 байта энтропии; SQLite хранит только SHA-256 от него. CSRF-токен отдельный, возвращается авторизованному клиенту и проверяется constant-time для изменений. CORS не включён, чужой Origin и Sec-Fetch-Site=cross-site отклоняются. Установлены CSP, nosniff, запрет iframe, Cache-Control=no-store. Swagger использует локальные JS/CSS; inline-скрипты запрещены и в Swagger; исключение для inline-стилей действует только на странице документации. Swagger UI 5.34.0 совместим с OpenAPI 3.1, поставляется с лицензией и не отправляет схему внешнему валидатору. Его request interceptor получает текущий CSRF из auth/me для изменяющих same-origin запросов. HTML-шаблон панели не доступен через публичный каталог статики.

Ограничение входа — 10 попыток за 5 минут по имени и адресу клиента. Валидационные ошибки не возвращают введённые значения паролей. Изменение пароля/удаление пользователя отзывает его сессии; история действий не удаляется.

## Границы этой версии

- Один рабочий процесс, один локальный SQLite-файл. `python -m backend.app.run` задаёт один worker; несколько реплик на разных машинах не поддерживаются. На сетевой файловой системе SQLite не размещать.
- Обычный пользователь имеет доступ ко всем платежам общей команды. Мультитенантность, персональные пространства и групповые права не предусмотрены кейсом.
- Список периодов без пагинации; подходит для небольшой команды, при больших объёмах потребуется пагинация и отдельный планировщик.
- История периодов материализуется до конца следующего календарного месяца. Календарь и бюджет вычисляют более далёкие даты без записи в БД; выбранный будущий период создаётся отдельной операцией.
- Удаление регулярного платежа останавливает будущую генерацию, но сохраняет уже созданные будущие записи как часть архива. Все сохранённые периоды видны в общей истории и доступны для исправления.
- Внешнюю ровно-однократную доставку Telegram гарантировать нельзя. Выбран режим без автоматического повтора неопределённой отправки; это может потребовать ручной проверки и пропустить сообщение после сбоя.
- Токен Telegram хранится в приватном `.env`/окружении. Ротация — через конфигурацию и рестарт. Приложение не управляет чужим ботом, сервером или DNS.
- Docker-конфигурация — отдельный вариант развёртывания. Её сборка и поведение на конкретном VDS требуют проверки на этой машине; автоматического изменения окружения сервера нет.
- Реализована идемпотентная транзакционная миграция v1/v2/v3 → v4 с сохранением пользователей, истории и состояний отправки. Другие неизвестные версии останавливают запуск. Перед обновлением сохраняйте резервную копию.


## Дополнительные каналы и файлы (v2)

`backend/app/notifications.py` поддерживает отдельную очередь для каждого из SMTP, webhook и in_app. Уникальность `(occurrence_id, channel)` сохраняет независимую дедупликацию и изоляцию ошибок. Поведение sent/uncertain аналогично Telegram: неизвестная доставка не повторяется. Восемь заведомо безопасных неудачных попыток переводят запись в uncertain для проверки администратором. SMTP sent означает приём DATA сервером.

SMTP использует ssl или starttls с проверкой сертификата по certifi (также работает в Python/macOS без глобальной установки CA). Режим none разрешён только для локального SMTP-теста. Для приёма DATA выделено до 30 секунд, чтобы дать провайдеру время на проверку письма. Один получатель предотвращает неоднозначную частичную доставку нескольким адресатам; Message-ID стабилен для периода/канала. Серверные ответы и исключения с секретами наружу не выводятся.

Webhook подписывается HMAC-SHA256 от `timestamp + "." + raw_body`, заголовки X-Invoice-Timestamp, X-Invoice-Signature и Idempotency-Key. Секрет задаётся в окружении. Адрес проверяется при каждой отправке: HTTPS, запрет credentials, fragment, внутренних/loopback/link-local/metadata адресов; все DNS-ответы должны быть публичными. Соединение привязано к единожды проверенному IP, а TLS сохраняет исходное имя сервера; перенаправления не выполняются. Только явный WEBHOOK_ALLOW_LOCALHOST разрешает HTTP на loopback для локального теста. Это не входящий Telegram webhook и не требует открывать входящий порт.

Уведомления панели доступны авторизованной команде. Отметки прочтения персональны. Браузерные уведомления показываются только после opt-in пользователя и при открытой странице; фонового Web Push нет. Для предотвращения потока старых уведомлений за проход показывается максимум три новых, локальная отметка не допускает повторного показа после обновления страницы.

`backend/app/telegram.py` обрабатывает кнопки через getUpdates, поэтому внешний HTTP-обработчик не нужен. Callback связан со случайным 24-байтным токеном, конкретным message_id, chat_id и разрешённым Telegram user_id. В личном чате доверен его владелец; в группе нужен TELEGRAM_ALLOWED_USER_IDS. Повторный callback не меняет уже сохранённую дату. Обработанный update_id и offset фиксируются в SQLite, действия пишутся в audit. Старые sent-сообщения получают кнопки через editMessageReplyMarkup, повторной отправки сообщения нет. Настроенный чужой Telegram webhook не удаляется: polling останавливается с сообщением в журнале процесса.

Чеки хранятся BLOB в SQLite, ссылки — отдельными записями той же таблицы attachments, с FK на конкретный период. Бэкап базы включает их автоматически. До 10 вложений на период, размер файла до 5 MiB, тип определяется по сигнатуре PDF/PNG/JPEG/WebP. ASGI-граница проверяет Host и ограничивает фактически принятые байты запроса (64 KiB JSON, 5 MiB + 128 KiB multipart), время передачи — 30 секунд. Подделанный Content-Length и chunked не обходят лимит. Для загрузок требуется Content-Length; авторизация и CSRF проверяются до разбора multipart, файлы выдаются только после авторизации с Content-Disposition: attachment и nosniff. HTML/SVG не принимаются, ссылки ограничены HTTP(S), сервер по ним не переходит.

## Локальный запуск и передача (v2.1)

`app.run --demo-webhook` запускает собственный loopback-приёмник после проверки свободного порта и его healthz; завершает только своего дочернего процесса. Настройки локального канала меняются в окружении текущего запуска, `.env` сохраняется. Uvicorn запускается с одним worker, пределом 16 одновременных соединений, backlog 128 и keepalive 5 секунд.

`backend/app/http_security.py` добавляет защитные заголовки и к ошибкам запросов. PUBLIC_BASE_URL задаёт внешний Origin за HTTPS-прокси; произвольные forwarded-заголовки не меняют доверенный адрес. `.env`, SQLite и её служебные файлы приватны. `backend/app/logging_security.py` скрывает известные секреты в аргументах и исключениях логгеров приложения, HTTP-клиента и Uvicorn.

`backend/app/audit.py` читает сохраняемый аудит через отдельную транзакцию-снимок. `/audit-log/page` применяет фильтры перед LIMIT/OFFSET; `snapshot_id` фиксирует верхний ID при навигации. Границы дат переводятся из APP_TIMEZONE в UTC, конечный день включён целиком. Индексы по времени, автору и действию добавляются идемпотентно. Старый `/audit-log` по-прежнему возвращает последние 100 событий. Панель показывает русские названия, результат и подробности изменения; история удалённых пользователей сохраняется. У платежных операций запись аудита входит в их write-транзакцию. Описание и сценарий защиты — [AUDIT.md](AUDIT.md).

Упаковщик использует явный состав исходников, отбрасывает символьные ссылки и известные локальные секреты, атомарно заменяет только готовый ZIP. Манифест SHA-256 и проверяющий скрипт позволяют сверить состав и целостность; это не цифровая подпись издателя. Чистая установка не содержит рабочих настроек/платежей.

Выбор параметров scrypt сверен с [OWASP Password Storage Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Password_Storage_Cheat_Sheet.html); проверка Origin/CSRF — с [OWASP CSRF Prevention Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Cross-Site_Request_Forgery_Prevention_Cheat_Sheet.html). Совместимость OpenAPI проверяется по [официальному Swagger UI](https://github.com/swagger-api/swagger-ui) и браузерному Try it out.


## Разовые платежи и рабочие процессы (v3)

Миграция v3 в той же транзакции добавляет `recurring_payments.frequency` (`monthly` / `once`) и `notes`. Старые определения получают monthly и пустое описание; исходные колонки и идентификаторы не меняются. Имя таблицы оставлено для совместимости API и связей. Значения неизвестной версии не мигрируются.

`materialize` для once создаёт ровно первый срок через уникальную пару (определение, дата), никогда не накапливая месяцы. `planning` включает только этот срок; произвольная новая дата once через calendar materialization запрещена. Оплата, вложения, очереди Telegram/SMTP/webhook/in_app и дедупликация используют тот же occurrence_id.

`/one-time-payments` отделяет создание и архив разового от обязательного monthly API. GET/POST возвращают PaymentOccurrence; DELETE принимает id периода. Monthly API не выдаёт/не архивирует once. Изменяющие операции сохраняют роли, CSRF и транзакционный аудит.

`backend/app/examples.py` добавляет шесть примеров с атомарными маркерами `demo.workflow.v3.*`. Он не переписывает существующие записи и не выполняет сетевых отправок. Новые неоплаченные примеры начинаются позже окна D−3; прошлый разовый пример сразу оплачен.

Фронтенд использует отдельные страницы overview/payments/history без новых фреймворков. История фильтрует оплаченные по paid_at, план — по due_date. Дизайн собран локальными слоями CSS, итоговый слой — apple.css. Темы обе поддерживаются, начальная light; сохранённая настройка приоритетна.


## Диагностика сервиса (v3.1)

`backend/app/service_logs.py` хранит JSONL отдельно от SQLite-аудита. Handler стандартного logging собирает сервер Uvicorn, приложение и библиотеки; ASGI middleware пишет коды/длительности/ID HTTP-запросов без body/headers/query. Процесс локального webhook пишет свой файл; API объединяет фиксированные имена обоих потоков. Rollover ограничивает общий объём 8 MiB, приватные права задаются при открытии, файлы/каталог не могут быть символическими ссылками. Ошибки логирования не меняют платежи и не прерывают запросы.

Жизненный цикл приложения подключает/снимает handler; один record не дублируется через logger propagation. Маскировка применяется до диска и на чтении, в том числе к traceback; фильтры стоят также на console handlers, поскольку фильтры родительского logger не обрабатывают дочерние записи. Системные логи доступны отдельным администраторским маршрутом `/api/v1/system-logs` и вкладкой в журнале. Ответ имеет явный Pydantic-контракт. Старые действия/доставка и их API сохранены. [SYSTEM_LOGS.md](SYSTEM_LOGS.md).
