# Устройство и ограничения

## Поток данных

```text
Browser (Next.js export) → net/http (auth + role + CSRF) → SQLite
                       │                   │
                       │             recurring_payments
                       │                   ↓ materialize
                       │             payment_occurrences
                       │                   ↓ unpaid, due ≤ today+3
                       └→ background worker → reminders → Telegram
                                            └→ deliveries → личный Telegram (срок/просрочка),
                                                            общий Telegram (просрочка), MAX, email, webhook
```

## Пакеты

```
internal/api/              сгенерированный из docs/openapi.json код (oapi-codegen)
internal/app/              HTTP-сервер: обработчики, маршруты, сборка зависимостей
internal/app/store/        SQLite: подключение, схема и миграции, app_state
internal/app/security/     хеши паролей, проверка слабых паролей, токены, шифрование, TOTP
internal/app/config/       настройки из окружения и .env
internal/app/audit/        журнал с HMAC-цепочкой
internal/app/schedule/     календарь: якорный день, периодичность, паузы, создание периодов
internal/app/wallet/       адреса кошельков и список OFAC
internal/app/notify/       очереди напоминаний и каналы: Telegram, MAX, email, webhook
internal/app/bot/          боты Telegram и MAX (доступ к платежам — через интерфейс bot.Backend)
```

Зависимости направлены вниз, без циклов: `store` ни от чего не зависит; `security` и `schedule` опираются на `store`; `config` — на `security`; `audit`, `notify`, `wallet`, `bot` — на нижние пакеты; `app` собирает всё вместе. Боты не импортируют сервер: что им нужно от платежей, описано интерфейсом `bot.Backend`, его реализует `app` (`bot_backend.go`). Очистку ключей воркер напоминаний вызывает через хук `Maintenance`.

`internal/app/config`: настройки из корневого `.env` и окружения (окружение приоритетнее). `internal/app/store`: схема v9, `foreign_keys`, WAL, busy_timeout; все записи — в транзакциях `BEGIN IMMEDIATE`. Старые версии обновляются при запуске в одной транзакции: новые таблицы и столбцы добавляются, а для разовых платежей столбец `frequency` пересоздаётся с `'once'` в CHECK. Версия новее известной останавливает запуск без изменения таблиц. Миграция v8 добавляет `claim_token`, отметку начала отправки в очередях, индексы и триггеры материализации. Старые записи `sending` считаются потенциально отправленными, чтобы обновление не разрешило повтор. Схема меняется только вперёд: перед выпуском нужна резервная копия, старый бинарник с v8 не запускается.

`internal/app/schedule`: календарные правила и материализация периодов; `internal/app/domain.go` — вычисление статуса и просрочки, суммы в целых копейках. Уникальность `(recurring_payment_id, due_date)` не позволяет дублировать период при одновременных чтениях.

`internal/app/removal.go`: удаление с отменой через `removed_at` отдельно от архивирования (`active=0`, `deleted_at`). Строки, даты оплаты и чеки сохраняются. Удалённый период остаётся исключением в графике: материализация и прогноз не создают его заново. Удалённые периоды и платежи исключены из списков, CSV, итогов, бюджета и напоминаний; прямые ссылки на периоды и чеки возвращают 404. Администратор восстанавливает запись через `/trash` («История → Удалённые платежи») или существующие restore API; `GET /api/v1/deleted-payments` возвращает элементы `payment` и `period`. При удалённом родителе его периоды отдельно не показываются. Восстановление родителя сохраняет прежние архив/паузу, а отдельно удалённые периоды остаются в корзине. Удаление и восстановление записываются в аудит; отправленные и неопределённые напоминания не сбрасываются.

`internal/app/server.go`, `handlers.go`, `validation.go`: маршруты (`http.ServeMux` с методами и `{id}`), строгая валидация JSON (лишние поля → 422, значения не возвращаются в ошибках), cookie-сессии и операции. При создании платежа и изменении оплаты сразу запускается фоновая проверка. Часы подменяются только в тестах через `Options.Today`; API для смены сегодняшней даты нет.

`internal/app/notify` (`reminders.go`): горутина с тикером и сохраняемое занятие задачи. Если проверку запросили во время прохода, выполняется ещё один проход. `Tick` ограничивает размер пачки; фоновый `Run` продолжает полную пачку через 250 мс без повторной материализации всей очереди. Пауза после 429 сохраняется в `app_state` и действует на новые задачи и после перезапуска. Короткая транзакция присваивает попытке случайный `claim_token`; следующая проверяет её владение, состояние платежа и получателя и фиксирует `dispatch_started_at`. Затем сеть вызывается **вне транзакции**, а результат записывается только при совпадении токена текущей попытки. Медленная отправка не удерживает SQLite write-lock. После фиксации начала отправки внешний запрос уже нельзя отозвать: последующая оплата или отвязка не гарантирует отмену сообщения в пути. До этой границы неактуальная задача отменяется; устаревший результат не перезаписывает новую попытку.

`internal/app/pages.go`: отдача страниц панели из `web/app` (статический экспорт `frontend/`, Next.js Pages Router + styled-components) с проверкой сессии и CSP по SHA-256 встроенных скриптов; `/_next/static` кешируется как immutable.

`docs/openapi.json` (OpenAPI 3.0.3) — источник правды для API: отдаётся на `/api/v1/openapi.json` и в Swagger, а `go generate ./internal/api` (oapi-codegen, версия закреплена директивой `tool` в `go.mod`) строит из неё `internal/api/api.gen.go`: типы, `ServerInterface` с методом на каждую операцию, маршрутизацию для `net/http` и встроенную копию спецификации. `internal/app/api_adapter.go` реализует интерфейс, вызывая обработчики, — операция в спецификации без обработчика не компилируется. Допустимые параметры строки запроса каждой операции берутся из спецификации (`api_routes.go`). В тестах каждый JSON-ответ проверяется на соответствие спецификации через kin-openapi (`contract_test.go`): весь набор тестов заодно контрактный. Порядок изменения API: правка спецификации → `go generate ./internal/api` → метод в адаптере → обработчик; CI проверяет, что сгенерированный код не устарел.

`internal/app/extension.go` и `extension/`: ключи API (`Authorization: Bearer ik_…`, в базе только SHA-256), предложения платежей с уникальным `source_key` и CORS без cookie только для двух эндпоинтов ключа. Само расширение — Manifest V3 с `activeTab`, `scripting`, `storage`; `detect.js` внедряется по клику и возвращает найденное во всплывающее окно. Папка `extension/` встроена в бинарник и отдаётся как `/extension.zip`.

`internal/app/recurring.go`, `account.go`, `telegram_links.go`, `receipts.go`, `budget.go`, `csv.go`: периодичность и пауза (`payment_pauses`; периоды внутри паузы не создаются, у платежа с паузами материализация идёт с первого периода, чтобы возобновление восстановило сроки), смена пароля обычного пользователя и TOTP администратора (секрет в `app_state`, повтор кода отклоняется по номеру шага), привязка Telegram (одноразовые коды как SHA-256), чеки в SQLite, бюджет с проекцией по правилу повторения, CSV с защитой от формул. Поиск и сравнение категорий в SQL используют зарегистрированные детерминированные функции `keeper_contains` и `keeper_equal` с Unicode-правилами Go: стандартные `NOCASE` и `lower()` SQLite понимают только ASCII. Пользовательские значения передаются параметрами.

`internal/app/budget.go`: план группируется по срокам оплаты, месяцам, категориям и валютам. Разовый платёж учитывается один раз, регулярный — по графику с учётом пауз; сохранённый период имеет приоритет над прогнозом. `remaining = max(0, planned - paid)`, где `paid` — суммы периодов с отметкой оплаты. Удалённые записи исключаются. В обзоре `summary.unpaid = total - paid` за текущий месяц, включая просроченное. Это учёт обязательств: банковские балансы и списания не запрашиваются и не сверяются. Проверка годового расчёта — `TestBudget` в `features_test.go`; `forecast_test.go` проверяет будущие периоды и оплату наперёд.

`internal/app/notify` (`deliveries.go`, `channels.go`) и `internal/app/bot` (`max.go`): второй outbox `deliveries` — одна строка на период, вид (`due` за 3 дня, `overdue` после срока, только за последнюю неделю) и канал (`telegram`, `telegram:<chat>`, `max`, `email`, `email:<contact_id>`, `webhook:<endpoint_id>`). Он использует ту же схему claim → проверка/фиксация начала → сеть без транзакции → условное сохранение по токену. Через 5 минут зависшая попытка с новым токеном, у которой отправка ещё не начиналась, может вернуться в `pending`; начатая или старая попытка становится `uncertain`. Неоднозначный результат не повторяется. Заведомо недоставленное повторяется не раньше чем через минуту, с учётом задержки транспорта, максимум 5 попыток, затем `failed`. Бот MAX работает long polling (`GET /updates`, marker в `app_state`), токен — в заголовке `Authorization`. Webhook подписывается HMAC-SHA256 и несёт стабильный `X-Invoice-Keeper-Delivery` для отсева повторов на стороне получателя. Очередь приветственных email также отправляет вне write-транзакции и проверяет `claim_token` при сохранении результата.

Личный Telegram для обоих видов напоминаний использует `deliveries`, включая сохранённые `attempts` и `retry_after`. Перед отправкой проверяются действующая привязка, назначенный ответственный и отсутствие совпадения с общим чатом; отвязка/перепривязка отменяет ожидающие и занятые записи до фиксации начала отправки. Уже начатая отправка сохраняет исход; её нельзя отменить и затем повторить как новую. Старую `personal_reminders` не переотправляют: её записи подавляют повторное напоминание `due` после обновления. Общий Telegram `due` остаётся в очереди `reminders` с прежней политикой повторов. Это разделение не даёт обещания внешней exactly-once доставки. Сценарии перезапуска, 429, двух соединений SQLite, смены получателя и неизвестного результата — в `telegram_delivery_test.go`.

`internal/app/sessions.go`: список сессий (публичный id — первые 16 символов SHA-256 токена, сам токен не раскрывается; `last_seen_at` пишется не чаще раза в минуту) и токены API. У ключа есть `access`: `extension` — только эндпоинты расширения, `read` — GET-запросы к данным, `write` — и изменения без CSRF (Bearer не отправляется браузером автоматически, поэтому CSRF-атака невозможна). Обработчики настроек аккаунта обёрнуты в `panelOnly`: по токену нельзя сменить пароль или второй фактор, выпустить токен или завершить сессии.

`internal/app/wallet` (адреса и список OFAC) и `internal/app/sanctions.go` (HTTP): кошелёк получателя (`wallet_network`, `wallet_address` и нормализованный `wallet_key`) и сверка со списком OFAC SDN. Валидация без внешних библиотек, кроме Keccak-256 из `x/crypto`: Base58Check и Bech32/Bech32m для BTC, EIP-55 для ETH, Base58Check с версией 0x41 для TRON. Список разбирается потоково (`encoding/xml`), в `sanctioned_addresses` попадают только криптоадреса, замена — одной транзакцией и только непустым списком. Результат сверки не хранится: платежи и периоды соединяются со списком по `wallet_key` при каждом чтении, поэтому обновление списка действует сразу, включая напоминания (для совпадений убирается ссылка «Оплатить»). Фоновая загрузка запускается, только если кошельки есть.

`internal/app/security` (пароли, токены, шифрование, TOTP), `internal/app/audit` (журнал), `internal/app/alerts.go`, `ratelimit.go`: шифрование значений XChaCha20-Poly1305 с именем поля в associated data (зашифрованное нельзя перенести в другую колонку), контрольное значение в `app_state` отличает неверный ключ от повреждённых данных; ключ процесса хранится в переменной пакета и задаётся `ConfigureEncryption` при старте сервера и в командах CLI. Журнал — HMAC-цепочка с «якорем» в `audit_head`; запись идёт внутри той же write-транзакции, что и действие, поэтому цепочка линейна. Ключ подписи — HKDF от `DATA_ENCRYPTION_KEY` («k») либо случайный ключ в `app_state` («s»); вид хранится у каждой записи, так что добавление ключа позже не ломает проверку старых записей. Пароли — Argon2id с ограничением одновременных вычислений (каждое берёт 64 МиБ). Лимит запросов — token bucket в памяти на адрес или токен.

`internal/app/audit_http.go`: `GET /api/v1/audit-log/page` добавляет к известным событиям платежей текущие название, состояние и срок периода. Исходные подписанные поля не меняются; это контекст для чтения, а не исторический снимок названия. Поиск `search` сопоставляется с названием, автором, кодом действия, entity и сроком без учёта регистра, включая кириллицу. Фильтры `from_date`/`to_date` относятся к времени события в `APP_TIMEZONE`, `actor` и `action` — точные значения; `snapshot_id` фиксирует верхнюю границу ID для страниц. Исторические события периодов/чеков до последней паузы показываются без названия и ссылки: прежняя пауза могла удалить период, после чего SQLite переиспользовал его ID. Консервативная проверка не позволяет связать старое действие с чужим платежом.

`frontend/lib/i18n.ts` и `lib/en.ts`: тексты пишутся по-русски в `t('…')`, английский — словарь; `npm run i18n` проверяет, что словарь полный и русского текста вне `t()` нет. Тема и язык хранятся в браузере.

`cmd/invoice-keeper`: команды `serve`, `bootstrap`, `backup`, `healthcheck`, `2fa-off`. `assets.go` встраивает `web/app` (через `all:`, иначе `go:embed` пропустит каталог `_next`), `web/swagger` и `docs/openapi.json`.

При падении после доставки, но до записи результата, остаётся `sending`. Через 5 минут запись становится `uncertain`; повторной отправки нет. Снятие отметки оплаты не сбрасывает `sent`. Только заведомо недоставленные попытки (ConnectError и явный 429) повторяются автоматически. Журнал отдаёт безопасное описание ошибки; URL с токеном и исходный ответ Telegram не сохраняются.

## Остановка

`cmd/invoice-keeper` ловит SIGINT и SIGTERM и останавливается по шагам: новые соединения не принимаются, текущие запросы завершаются (до 10 с, затем соединения закрываются), фоновые задачи получают отмену контекста и завершаются (до 15 с), и только потом закрывается база. Каждая фоновая задача — `Run(ctx)`: воркер напоминаний не начинает новые проходы и выходит между сообщениями, никогда не посреди отправки; боты обрывают длинный опрос сразу, но дорабатывают уже полученные обновления и сохраняют смещение; загрузка списка OFAC прерывается. Дожидаются и проходов, запущенных из запросов (`Kick`), и уведомлений о входе. Если что-то не уложилось в срок, процесс выходит, не закрывая базу под незавершённой работой: SQLite остаётся согласованной, а сообщение, прерванное посреди отправки, при следующем запуске станет «Нужна проверка», без повторной отправки. Повторный Ctrl+C завершает процесс сразу. В `compose.yaml` `stop_grace_period: 30s`, чтобы Docker не убил контейнер раньше.

## Авторизация

Пароли: Argon2id с индивидуальной случайной солью (64 МиБ, 3 прохода, параллелизм 4), формат PHC. Старые scrypt-хеши проверяются для совместимости и обновляются при успешном входе. Администратор — виртуальная учётная запись `id=0` из `ADMIN_USERNAME`/`ADMIN_PASSWORD`, без строки в `users`; users API не создаёт, не редактирует и не удаляет её. Отпечаток admin-настроек привязан к сессии, поэтому смена учётных данных после рестарта отзывает старую сессию.

Ограничение относится к идентичности и паролю администратора. Его email и подтверждение хранятся в `email_contacts`, Telegram-привязка — в `telegram_links`, TOTP — в `app_state`; эти настройки доступны через «Аккаунт», как и управление сессиями и токенами. Контактный адрес не становится логином. Пароль обычного пользователя хранится в `users` и меняется через панель. Настройки аккаунта требуют cookie-сессии, а не API-токена.

Случайный session token содержит 32 байта энтропии; SQLite хранит только SHA-256 от него. CSRF-токен отдельный, возвращается авторизованному клиенту и проверяется constant-time для изменений. CORS не включён, чужой Origin и Sec-Fetch-Site=cross-site отклоняются. Установлены CSP, nosniff, запрет iframe, Cache-Control=no-store. Swagger использует локальные JS/CSS; inline-разрешение CSP относится только к странице документации. HTML-шаблон панели не доступен через публичный каталог статики.

Ограничение входа — 10 попыток за 5 минут по имени и адресу клиента. Валидационные ошибки не возвращают введённые значения паролей. Изменение пароля/удаление пользователя отзывает его сессии; история действий не удаляется.

## Границы этой версии

- Один рабочий процесс, один локальный SQLite-файл. `invoice-keeper serve` — один процесс; несколько реплик на разных машинах не поддерживаются. На сетевой файловой системе SQLite не размещать.
- Обычный пользователь имеет доступ ко всем платежам общей команды. Мультитенантность, персональные пространства и групповые права не предусмотрены кейсом.
- Список периодов без пагинации; подходит для небольшой команды, при больших объёмах потребуется пагинация и отдельный планировщик.
- Периоды материализуются до конца следующего календарного месяца. Более поздние сроки календарь берёт из графика (`GET /api/v1/payment-forecast`) и показывает пунктиром; такой срок можно оплатить заранее (`POST /api/v1/recurring-payments/{id}/periods`), тогда период создаётся сразу, а планировщик потом его не дублирует (UNIQUE по платежу и сроку). Пауза удаляет только неоплаченные периоды, оплаченные заранее остаются.
- Архивирование (`DELETE /recurring-payments/{id}`) прекращает генерацию и напоминания, сохраняя периоды в истории и итогах. Удаление (`?mode=delete` или DELETE отдельного периода) исключает записи из рабочих представлений до восстановления через корзину; физического стирания нет.
- Внешнюю ровно-однократную доставку Telegram гарантировать нельзя. Выбран режим без автоматического повтора неопределённой отправки; это может потребовать ручной проверки и пропустить сообщение после сбоя.
- Доставку в MAX, email и webhook тоже нельзя гарантировать ровно один раз: неоднозначный результат помечается `uncertain` без повтора; webhook-получатель может отсеять повтор после 5xx по `X-Invoice-Keeper-Delivery`.
- Токен Telegram хранится в приватном `.env`/окружении. Ротация — через конфигурацию и рестарт. Приложение не управляет чужим ботом, сервером или DNS.
- Для MAX обязательны действующие `MAX_BOT_TOKEN` и числовой `MAX_CHAT_ID`; дополнительные доверенные корни задаются `MAX_CA_FILE`. Тестовый транспорт проверяет код, но не доступность платформы или реальную доставку. SMTP, webhook и Telegram также требуют отдельной проверки конфигурации.
- Проверка типов, контракта API и серверного рендера не заменяет визуальную проверку в браузере. Ограниченный доступ тестового инструмента к локальному адресу не доказывает неисправность приложения; непроведённый браузерный сценарий остаётся непроверенным.
- Docker-конфигурация — отдельный вариант развёртывания. Её сборка и поведение на конкретном VDS требуют проверки на этой машине; автоматического изменения окружения сервера нет.
- Миграции только вперёд: старый бинарник нельзя запускать с более новой схемой. Перед обновлением рабочей базы нужна резервная копия.


Личные email-уведомления: `email_contacts` хранит контакт пользователя или администратора, подтверждение, переключатель уведомлений и очередь приветственного письма. API создания участника требует email; миграция сохраняет существующих пользователей без адреса. Одноразовый код действует 24 часа: SHA-256 для проверки, временная шифрованная копия для отправки, очистка после отправки. Публичная страница `/confirm-email` берёт код из URL fragment, удаляет его из адресной строки и подтверждает POST-запросом. GET не активирует адрес. Повторная отправка ограничена одной в минуту и аннулирует старый код.

Личные напоминания хранятся в `deliveries` с каналом `email:<contact_id>` и снимком `recipient`. Получатели — подтверждённый ответственный либо администратор для платежей без ответственного. Перед отправкой повторно проверяются подтверждение, адрес, подписка, назначение и состояние платежа. Отправленные и неоднозначные результаты не повторяются; смена адреса или ответственного отменяет ожидающие отправки. Прежний `SMTP_TO` остаётся отдельным общим каналом, а для личной почты он не требуется. Журнал администратора показывает адрес получателя. SMTP-очередь использует прежнюю модель защиты от дубликатов при неизвестном исходе.


## Живые обновления панели

`store.DB.Write` сравнивает `total_changes()` на одном SQLite-соединении до/после транзакции и публикует сигнал только после успешного commit с изменениями. Откат и чтение не создают событие. Подписчики имеют буфер в один сигнал: медленный клиент не тормозит запись и не накапливает неограниченную очередь. Прямые изменения через SQL вне `DB.Write` не публикуют сигнал; резервное перечитывание раз в минуту остаётся.

`GET /api/v1/events` принимает cookie-сессию, проверяет Origin, отправляет `ready`/`changed` с номером ревизии без бизнес-данных. При переподключении клиент получает свежий снимок через API; `Last-Event-ID` не обещает воспроизведение пропущенных событий. Поток ограничен шестью подключениями на сессию и 128 на процесс, heartbeat и read-only проверка сессии выполняются каждые 15 секунд и перед изменениями. Завершение сессии отправляет `session-ended`. На каждый flush установлен пятисекундный deadline; shutdown закрывает потоки. Nginx не буферизует этот маршрут. `keeper_sse_connections` отражает число подключений; длительность SSE не входит в гистограмму обычных HTTP-запросов.

Frontend объединяет сигналы за одну секунду. Для каждого набора фильтров выполняется один запрос; новые сигналы ставят только одно повторное чтение. Успешный ответ текущего запроса отображается, а не отбрасывается из-за непрерывной рассылки. Изменение фильтров отключает принятие устаревшего ответа. Скрытая вкладка закрывает поток, при возвращении перечитывает состояние. Открытый диалог откладывает обновление до закрытия; черновик формы сохраняется. Механизм рассчитан на один процесс приложения, не заменяет межсерверную шину событий.

## Графический месячный отчёт Telegram

`report.go` использует тот же `calculateBudget`, что и годовой веб-бюджет. Все выборки выполняются в одном deferred read snapshot, без write-lock. `internal/app/report` рисует PNG в Go с кириллическим шрифтом, без внешнего chart-сервиса. Каждый запрос заново читает бюджет; ограниченный кэш хранит только PNG (12 картинок, 20 секунд), ключ включает содержимое, месяц, валюту, день, ревизию и минуту формирования. После изменения состояния картинка не берётся из устаревшего кэша.

`/report` и inline-кнопки доступны подключённому командному чату и привязанным личным чатам. Перед отправкой привязка проверяется повторно. Месяцы ограничены 2000–2100, валюты — RUB/USD/EUR. `sendPhoto` создаёт отчёт, `editMessageMedia` меняет его; неоднозначный сетевой результат не повторяется автоматически. PNG — интерактивный отчёт через кнопки Telegram, а не график с наведением внутри изображения.


## Ограниченные списки и материализация

Панель использует `GET /payment-occurrences/page` и `/recurring-payments/page`: по 25 записей, API допускает до 100. Фильтрация, сортировка и подсчёт выполняются в SQL; расшифровывается и сериализуется выбранная страница. Платежи и история поддерживают поиск по названию/описанию, Unicode-категории и раздельные даты: срок либо фактическая дата оплаты с fallback на срок для неоплаченного архива. Старые полные endpoints и CSV остаются для совместимости и экспорта, поэтому их размер всё ещё зависит от всего результата. Полный список периодов и CSV пишутся построчно в приватный временный файл рядом с SQLite (права 0600), затем передаются клиенту; весь массив и ответ не держатся в RAM. Одновременно разрешены два таких ответа, ожидание отменяется вместе с запросом. Перед отправкой HTTP-ответа чтение БД уже завершено, поэтому медленный клиент не удерживает соединение. Файл удаляется после успеха, ошибки или отмены; после аварийного завершения процесса может остаться `.invoice-keeper-response-*`. Для экспорта нужен свободный диск под размер ответа; автоматического широкого удаления файлов нет. Базы в памяти используют системный временный каталог.

`GET /payments/overview` возвращает общие счётчики и ограниченные очереди. Обзор и боковая панель используют один запрос из контекста сессии. `/payments/calendar` возвращает суммы и количество по всем дням, но не более трёх карточек на день; полный выбранный день загружается через `/payments/calendar/day` страницами по 25 записей. Итоги учитывают все сохранённые и прогнозные обязательства, даже если показаны только первые карточки. `/notifications?limit=50&page=…` возвращает страницу без расшифровки платёжных реквизитов, общий `unread_count` и до 100 последних событий `browser_items`.

`ensureMaterialized` проверяет рабочий день и флаг изменения расписаний в `app_state`. Триггеры расписаний и пауз устанавливают флаг в той же транзакции; успешная материализация снимает его. Откат не оставляет ложный сброс, изменения через другое соединение также учитываются. Повторное чтение без изменений не обходит все расписания и не требует write-lock. Списки, счётчики, календарь и бюджет читают согласованный read snapshot. Это оптимизация одного приложения с SQLite, а не обещание неограниченной нагрузки или распределённых workers.

## Браузерные напоминания

Доставка подключена в `Shell` и работает во всех открытых разделах панели. Это функция сайта, отдельно от расширения для импорта платежей. Пользователь включает её в «Уведомлениях» и разрешает показ в браузере; кнопка «Проверить» позволяет проверить разрешение системы. При первом подключении текущая история становится исходным состоянием, чтобы не показывать накопившиеся события сразу. Новые события проверяются через общую ленту и резервный минутный опрос; несколько новых записей могут объединяться в сводное уведомление. Обработчик использует последние 100 событий и не обещает отдельное системное окно для каждого события массовой загрузки. Закрытая или приостановленная браузером панель не обеспечивает доставку; для неё нужны Telegram или email.

Команды Telegram `/todo` и `/overdue` считают количество и итоги в SQL, выбирая один платёж на страницу. Текстовый ответ MAX показывает до десяти строк с полным итогом раздела и ссылкой на панель; все платежи в память ради короткого сообщения не загружаются.

### Несколько webhook-получателей (schema 10)

`internal/app/webhooks` хранит получателей в БД; прежняя `.env` настройка импортируется однократно после настройки шифрования. `/api/v1/webhooks` управляет адресами через admin-session + CSRF. Отключение/удаление отменяет только pending и ещё не начатые sending. Worker читает URL и секрет под write lock непосредственно перед фиксацией dispatch; смена URL/секрета при уже начатом запросе запрещена. Параллельный пул2 webhook использует round-robin адресов, максимум один sending на адрес, независимые retry/backoff и stable delivery IDs. Он не удерживает DB write lock во время сети. Metrics агрегирует динамические `webhook:<id>` в фиксированный label `webhook`; адреса и имена в метрики не попадают.
