# Invoice Keeper

Регулярные платежи команды: панель на русском, отдельные периоды оплаты, история, просрочки и напоминания в Telegram за 3 дня. RUB, USD и EUR считаются отдельно, без конвертации.

Стек: бэкенд на Go 1.27 (стандартный `net/http`, SQLite через `modernc.org/sqlite` — без CGO). Панель — **Next.js 16 (Pages Router) + React 19 + styled-components**, собранная как статический экспорт и встроенная в бинарник вместе со Swagger UI и OpenAPI. Фоновая проверка напоминаний работает внутри того же процесса; Redis, внешняя БД и CDN не нужны. Собранная панель лежит в `web/app`, поэтому **для запуска нужен только Go** — Node.js требуется лишь для изменения фронтенда.

## Быстрый локальный запуск

Нужен Go 1.27+ (https://go.dev/dl/; на Windows: `winget install GoLang.Go`). Команды выполняются в папке проекта.

```sh
go run ./cmd/invoice-keeper bootstrap --demo
go run ./cmd/invoice-keeper
```

Или собрать один файл и запускать его без Go:

```sh
go build -o bin/invoice-keeper ./cmd/invoice-keeper     # Windows: bin/invoice-keeper.exe
./bin/invoice-keeper bootstrap --demo
./bin/invoice-keeper serve
```

Откройте **http://127.0.0.1:18080**. Логин администратора — `ADMIN_USERNAME`, пароль — `ADMIN_PASSWORD` в локальном `.env`. Bootstrap генерирует уникальные пароли; общедоступного стандартного пароля нет. Для обычного пользователя используйте `DEMO_USERNAME` / `DEMO_PASSWORD` из того же файла.

`--demo` добавляет шесть платежей с относительными датами: аренду, сервер, Notion, домен, Figma и интернет. Среди них есть оплаченные и просроченные периоды, используются все три валюты. При повторном запуске существующие настройки и непустая база сохраняются без повторного наполнения.

Для пустой рабочей базы выполните `invoice-keeper bootstrap` **без** `--demo`. Для собственного `.env` используйте `.env.example`: замените `ADMIN_PASSWORD` на случайный пароль длиной 12–128 символов. Bootstrap не перезаписывает `.env`. Переменные окружения имеют приоритет над файлом.

По умолчанию приложение слушает только `127.0.0.1`. Остановить его можно через Ctrl+C (или SIGTERM): текущие запросы и фоновые задачи завершаются, затем закрывается база; повторный Ctrl+C — немедленный выход. Данные останутся в `data/invoice-keeper.sqlite3`. Другой локальный порт: `invoice-keeper serve --port 18082`.

## Фронтенд

Исходники панели — в `frontend/` (TypeScript): `pages/` — экраны (платежи, регулярные, календарь, команда, журнал, вход), `components/` — каркас, модальные окна и UI-примитивы на styled-components, `lib/` — клиент API, сессия и форматирование. После правок пересоберите панель и Go-бинарник:

```sh
cd frontend
npm ci
npm run build      # next build → статический экспорт → копия в ../web/app
cd ..
go run ./cmd/invoice-keeper
```

Страницы панели отдаёт Go и только после проверки сессии: без входа `/`, `/recurring`, `/calendar`, `/team`, `/activity` перенаправляют на `/login`. CSP каждой страницы разрешает встроенный загрузочный скрипт Next.js только по его SHA-256 (хеши вычисляются при запуске), `unsafe-inline` для скриптов не используется. Для стилей он разрешён: styled-components добавляет их во время работы. Файлы `/_next/static/*` имеют хеш в имени и кешируются браузером навсегда.

## Браузерное расширение

Расширение подтягивает регулярные платежи из кабинетов сервисов (хостинги, SaaS, подписки): находит на открытой странице сумму, валюту и дату следующей оплаты и отправляет их в «Предложения», где администратор принимает или отклоняет.

1. В панели откройте **Расширение** → «Скачать расширение» (или возьмите папку `extension/` из репозитория).
2. `chrome://extensions` или `edge://extensions` → «Режим разработчика» → «Загрузить распакованное» → папка расширения. В Firefox: `about:debugging` → «Загрузить временное дополнение» → `manifest.json`.
3. В окне расширения укажите адрес сервера и нажмите **«Подключить»**: откроется панель (при необходимости — вход), подтвердите подключение и снова нажмите на значок расширения — ключ придёт сам. Расширение создаёт случайный код на 256 бит, панель выпускает ключ под его хешем на 10 минут, расширение забирает ключ один раз; незабранный ключ удаляется. Ручной ввод ключа остался в настройках расширения.
4. На странице с услугами нажмите на иконку Invoice Keeper, проверьте найденное и отправьте.

Приватность: разрешение только `activeTab` — страница читается, только когда пользователь нажал на иконку; фоном ничего не читается. Банки и почта в стоп-листе. Распознавание идёт в браузере, на сервер уходят только название, сумма, валюта, дата и адрес страницы. Ключ API работает только на `/extension/whoami` и `POST /payment-suggestions`, хранится в базе как SHA-256 и удаляется вместе с пользователем. Ключ расширения действует год (при ручном создании срок можно выбрать), а любой ключ или токен, которым не пользовались `KEY_IDLE_DAYS` дней (по умолчанию 90), отключается и удаляется. Повторная отправка того же платежа не создаёт дубль: неразобранное предложение обновляется, принятое или отклонённое не меняется.

Распознавание: выделенный текст, таблицы с колонками «Цена» и «Действует до / Следующее списание», а также блоки страницы, где рядом стоят сумма и дата. Годовые платежи помечаются и по умолчанию не отмечены (система повторяет ежемесячно).

## Возможности

- **Периоды:** ежемесячно, ежеквартально или ежегодно; дата считается от первой оплаты (31.01 → 28.02 → 31.03, 29.02 раз в год → 28.02). Ближайший срок виден сразу.
- **Пауза:** до даты или до возобновления. Новых периодов и напоминаний нет, пропущенные месяцы не становятся просрочкой.
- **Категории и ответственный:** фильтры в списке и выгрузке, «Только мои» у пользователя, бюджет по категориям. Изменение названия, суммы (для неоплаченных периодов с сегодняшнего дня), категории и ответственного.
- **Чеки и ссылки** у конкретного периода: PDF, PNG, JPEG, WebP до 5 МБ, тип определяется по содержимому.
- **Бюджет на год** по месяцам и категориям, отдельно по валютам; будущие месяцы считаются по правилу повторения. **Итоги на дату** во вкладке «Платежи».
- **CSV:** выгрузка периодов с фильтрами (открывается в Excel), импорт регулярных платежей с проверкой каждой строки без записи; UTF-8 и Windows-1251.
- **Telegram:** кнопка «✅ Оплачено» в напоминании, команды `/todo`, `/overdue`, `/chatid`, `/help`. Привязка Telegram к аккаунту одноразовой ссылкой: личные напоминания ответственному и администратору; отметка из лички записывается от имени пользователя панели. Без `TELEGRAM_CHAT_ID` напоминания идут только в личку привязанным.
- **Аккаунт:** смена своего пароля (остальные сессии завершаются), двухфакторный вход администратора по TOTP с QR-кодом. Восстановление без телефона: `invoice-keeper 2fa-off` на сервере.
- **Ссылка на оплату и реквизиты** у платежа: кнопка «💳 Оплатить» в напоминаниях Telegram и MAX, ссылка в письме и webhook, значок 💳 у неоплаченного периода в панели. Ссылка — только `http(s)`.
- **Просрочка:** на следующий день после неоплаченного срока — одно повторное напоминание «⚠️ Платёж просрочен» в те же каналы (`OVERDUE_REMINDERS=false` выключает). Старые долги старше недели не рассылаются.
- **Каналы напоминаний:** Telegram (общий чат и личка), **MAX** (общий чат, кнопка «Оплачено», команды `/todo`, `/overdue`, `/chatid`), **email** через SMTP, **webhook** с подписью HMAC-SHA256 — подходит для входящих webhook Slack, Mattermost и Discord. Журнал отправки по каждому каналу — во вкладке «Журнал».
- **Криптокошелёк получателя и сверка с санкциями OFAC:** у платежа можно указать кошелёк в сетях BTC, Ethereum/EVM (USDT/USDC ERC-20) или TRON (USDT TRC-20). Адрес проверяется по формату и контрольной сумме, затем сверяется со списком SDN Минфина США. При совпадении платёж помечается ⛔, в напоминаниях — предупреждение и нет кнопки «Оплатить», в журнал пишется событие. Проверить любой адрес без сохранения можно во вкладке «Журнал».
- **Токены API** для скриптов: «Аккаунт» → «Токены API», доступ «только чтение» или «чтение и запись», срок 30/90/365 дней или бессрочно. Токен показывается один раз; пароль, второй фактор, токены и сессии по нему не изменить.
- **Активные сессии:** устройство, адрес и последняя активность; завершить одну или все, кроме текущей.
- **Графики бюджета:** столбики по месяцам и полосы по категориям (оплачено/осталось) в выбранной валюте, подсказки при наведении и с клавиатуры, клик по месяцу открывает его в календаре. **Сортировка** списка платежей по клику на заголовок столбца.
- **Интерфейс:** тёмная и светлая тема (по умолчанию как в системе), русский и английский, вкладка «Помощь» с правилами этого сервера.

- Вход, выход, две роли, cookie-сессии. Администратор задаётся в `.env`; через панель его учётная запись не управляется.
- Администратор добавляет и прекращает регулярные платежи, создаёт, изменяет и удаляет обычных пользователей.
- Пользователь видит общий список, подтверждает/отменяет оплату конкретного периода, исправляет фактическую дату. Эти ограничения проверяются и в API.
- Обзор по месяцам, поиск, фильтры по валюте и статусу, календарь, история действий и журнал Telegram.
- Платёж архивируется мягко: существующие периоды и история сохраняются; новые периоды и напоминания прекращаются.
- SQLite сохраняет платежи, оплаты, пользователей, сессии, журнал и состояния отправки после перезапуска.

## Правила дат и сумм

`APP_TIMEZONE=Europe/Moscow` определяет текущую дату. Срок и фактическая дата — календарные даты `YYYY-MM-DD`. Оплата в день срока своевременна; просрочка начинается на следующий день. Для оплаченного периода число дней просрочки считается по фактической дате, для неоплаченного — по сегодняшней. Исправление фактической даты пересчитывает просрочку, срок остаётся прежним. Будущая фактическая дата не допускается. При отмене оплаты дата очищается.

Суммы хранятся целым числом копеек/центов; API передаёт их десятичными строками. У каждой валюты свои итоги. В summary `unpaid` включает просроченные суммы, `overdue` — часть `unpaid`, а `total = paid + unpaid`. Фильтрация итогов идёт по **сроку оплаты**, а не по дате фактического платежа. Архивные периоды входят в историю и итоги; `include_archived=false` исключает их.

Якорь повторения — день первой оплаты. Пример: **31 января → 28 февраля → 31 марта → 30 апреля**; в високосном феврале — 29-е. Оплата и просрочка не влияют на создание следующих периодов. Периоды создаются до конца следующего календарного месяца включительно, а при добавлении далёкого будущего платежа создаётся его первый период. Проверка выполняется при запуске, чтении списка и в фоне. Будущие месяцы вне этого горизонта пока пусты.

## Telegram

По умолчанию `TELEGRAM_ENABLED=false`: приложение не отправляет сообщения и не имитирует успешную отправку.

1. Создайте бота через официальный BotFather и добавьте его в нужный чат с правом отправки сообщений.
2. Узнайте числовой `chat_id` своего чата; для группы он обычно отрицательный. Токен не передавайте в переписках и не добавляйте в Git.
3. В локальном `.env` задайте `TELEGRAM_BOT_TOKEN`, `TELEGRAM_CHAT_ID`, `TELEGRAM_ENABLED=true`.
4. Перезапустите приложение. При необходимости создайте тестовый платёж со сроком через 1–3 дня.

Неоплаченный активный период попадает в отправку за 3 дня до срока; если добавлен позже — проверка запускается сразу после создания. Фон проверяет сроки каждые 60 секунд. Сообщение содержит название, сумму, валюту и срок. Оплаченные и архивные периоды не отправляются. В одном проходе отправляется не более 20 сообщений; оставшаяся очередь обрабатывается в следующих проходах.

**Защита от дублей:** у периода одна запись отправки с уникальным ключом. Перед сетевым запросом фиксируется `sending`. Успешный ответ сохраняет `sent` и `message_id`; повторной отправки не происходит даже после отмены оплаты или перезапуска. Два одновременно работающих обработчика используют транзакции SQLite для взаимного исключения.

Telegram `sendMessage` не имеет ключа идемпотентности. Если соединение оборвалось после возможной доставки, одновременно гарантировать повторную доставку и отсутствие дублей невозможно. Здесь выбран приоритет отсутствия дублей: таймаут/неоднозначный ответ переводит запись в `uncertain`, и автоматический повтор блокируется. После падения процесса зависший `sending` через 5 минут также становится `uncertain`. Проверьте чат и настройки по разделу **Журнал**; скрытых повторов нет. При невозможности установить соединение или явном ответе 429 разрешён отложенный повтор. Для повторного получения неопределённого напоминания автоматической кнопки нет — это осознанное ограничение.

Реальная доставка требует действительных токена, чата и доступа сервера к `api.telegram.org`; без них проверена логика с имитацией ответов API.

## Безопасность

- **Пароли** — Argon2id (RFC 9106: 64 МиБ, 3 прохода); хеши прежних версий (scrypt) обновляются при следующем входе. Пароли из списков утечек (встроенный список, без запросов в сеть), с логином внутри, из одного-двух символов и клавиатурные последовательности не принимаются — в том числе слабый `ADMIN_PASSWORD` не даст запустить сервер.
- **Шифрование в базе** — секрет второго фактора, файлы и ссылки чеков, реквизиты платежей шифруются XChaCha20-Poly1305 ключом `DATA_ENCRYPTION_KEY` (его создаёт `bootstrap`, вручную — `invoice-keeper keygen`). Ключ в базе не хранится, поэтому утёкшая база или бэкап без `.env` этих данных не раскрывают. При добавлении ключа к существующей базе старые значения шифруются при запуске. Без ключа или с чужим ключом зашифрованная база не откроется. **Потеря ключа = потеря зашифрованных данных**: храните копию отдельно.
- **Журнал защищён от подмены** — каждая запись подписана HMAC вместе с хешем предыдущей, отдельно хранится «якорь» последней записи. Изменение, вставка или удаление записи (в том числе последних) видны в «Журнале» и в `GET /api/v1/audit-log/verify`. С `DATA_ENCRYPTION_KEY` ключ подписи выводится из него, и пересчитать цепочку, имея только доступ к базе, нельзя.
- **Сессии и запросы** — cookie `HttpOnly`, `SameSite=Strict`; изменяющие запросы требуют CSRF-токен **и** заголовок `Origin` этого сайта; неизвестные параметры строки запроса отклоняются; лимит попыток входа и общий лимит запросов к API (`RATE_LIMIT_PER_SECOND`, `RATE_LIMIT_BURST`).
- **Уведомления** — о каждом входе (устройство, адрес, время) и о блокировке после серии неверных паролей в привязанный Telegram владельца аккаунта (`LOGIN_ALERTS`).
- **Кнопка «Оплачено» в Telegram** по умолчанию принимается только от участников, привязавших аккаунт в панели (`TELEGRAM_PAID_LINKED_ONLY`). В MAX — от участников чата `MAX_CHAT_ID`.
- **Заголовки** — строгая CSP без `unsafe-inline` для скриптов, `X-Frame-Options: DENY`, COOP/CORP `same-origin`, HSTS при `COOKIE_SECURE=true`.
- **При запуске** сервер предупреждает, если `.env` доступен на чтение другим пользователям системы.
- **CI** — `govulncheck`, `gosec`, `npm audit`; Dependabot присылает обновления зависимостей. Сборка закреплена на исправленном Go (`toolchain` в `go.mod`).

## MAX, email и webhook

Все каналы необязательны и включаются переменными в `.env`; без них приложение работает как раньше. У каждой отправки своя запись в базе (период × вид напоминания × канал), поэтому сообщение уходит один раз даже после перезапуска. Как и в Telegram, неоднозначный результат (`uncertain`) автоматически не повторяется; заведомо недоставленное (нет соединения, 429/5xx) повторяется позже, но не больше 5 попыток, затем `failed`. Состояние каждой отправки — во вкладке **Журнал** → «другие каналы и просрочка» и в `GET /api/v1/deliveries`.

- **MAX:** создайте бота на платформе MAX для партнёров, добавьте его в чат и задайте `MAX_BOT_TOKEN` и `MAX_CHAT_ID` (ID подскажет команда `/chatid` в чате с ботом). Токен передаётся в заголовке `Authorization`, не в URL. Кнопку «✅ Оплачено» принимает только этот чат. Если система не доверяет сертификату API MAX (он может быть выпущен российским национальным УЦ), укажите путь к корневому сертификату в `MAX_CA_FILE`. Адрес API меняется через `MAX_API_URL`.
- **Email:** `SMTP_HOST`, `SMTP_FROM`, `SMTP_TO` (через запятую), при необходимости `SMTP_USERNAME`/`SMTP_PASSWORD`. `SMTP_SECURITY=starttls` (587, по умолчанию), `ssl` (465) или `none`. Для Яндекса: `smtp.yandex.ru`, `SMTP_SECURITY=ssl`, пароль приложения.
- **Webhook:** `WEBHOOK_URL` получает `POST` с JSON: `event` (`reminder.due` или `reminder.overdue`), `occurrence` (id, название, сумма, валюта, срок, ссылка и реквизиты), а также `text` и `content` для Slack/Mattermost/Discord. Заголовок `X-Invoice-Keeper-Delivery` одинаков для повторов одного напоминания — по нему получатель отбрасывает дубли. С `WEBHOOK_SECRET` добавляется `X-Invoice-Keeper-Signature: sha256=<HMAC-SHA256 тела>`.

## Сверка кошельков с санкциями OFAC

Источник — официальный список SDN Минфина США (`SDN.XML`, около 30 МБ), из него берутся идентификаторы «Digital Currency Address». Список скачивается автоматически раз в `OFAC_REFRESH_HOURS` (по умолчанию 24) и **только пока хотя бы у одного активного платежа указан кошелёк** — установка без криптоплатежей к OFAC не обращается. Вручную: кнопка «Обновить список» в «Журнале» или `invoice-keeper ofac-update`; для сервера без интернета — `invoice-keeper ofac-update --file SDN.XML`. Неудачная или пустая загрузка не затирает прежний список. Выключить: `OFAC_ENABLED=false`.

Сверка идёт по адресу независимо от того, под какой монетой он указан в списке: у OFAC встречаются USDT-адреса в TRON и Ethereum и даже TRON-адрес с пометкой XBT. Адреса Ethereum и Bech32 сравниваются без учёта регистра.

Ограничение: ловятся только адреса, которые OFAC опубликовал. Это не оценка риска по истории транзакций (связи с миксерами, мошенничеством и т. п.) — для неё нужен внешний провайдер.

## API и Swagger

После входа откройте **http://127.0.0.1:18080/api/v1/docs**. Экспорт спецификации: [`docs/openapi.json`](docs/openapi.json); актуальная схема — `/api/v1/openapi.json`. Все данные и Swagger требуют авторизации.

Основные маршруты:

| Метод | Маршрут | Доступ |
|---|---|---|
| POST | `/api/v1/auth/login` | Вход |
| GET | `/api/v1/auth/me` | Авторизованные |
| POST | `/api/v1/auth/logout` | Авторизованные + CSRF |
| GET / POST | `/api/v1/recurring-payments` | Все / администратор |
| DELETE | `/api/v1/recurring-payments/{id}` | Администратор |
| GET | `/api/v1/payment-occurrences` | Все |
| GET / PATCH | `/api/v1/payment-occurrences/{id}` | Все |
| GET | `/api/v1/payments/summary` | Все |
| GET / POST | `/api/v1/users` | Администратор |
| PATCH / DELETE | `/api/v1/users/{id}` | Администратор |
| GET | `/api/v1/docs` | Все |

Дополнительные маршруты: `/settings`, `/reminders`, `/deliveries`, `/sanctions`, `/audit-log`, `/me/sessions`, `/api-keys` под префиксом `/api/v1`. `/healthz` возвращает только доступность приложения и базы.

Изменяющие запросы с cookie должны нести заголовок `Origin` этого сайта — браузер добавляет его сам, а для `curl` и скриптов удобнее токен API.

**Токены API.** Вместо cookie можно передать `Authorization: Bearer ik_…` — токен из «Аккаунт» → «Токены API». Токен `read` разрешает GET-запросы к данным, `write` — ещё и изменения (X-CSRF-Token не нужен: токен не отправляется браузером сам). Права — как у владельца. Настройки аккаунта (пароль, второй фактор, токены, сессии, привязка Telegram) по токену недоступны. Пример: `curl -H "Authorization: Bearer ik_…" http://127.0.0.1:18080/api/v1/payments/summary`.

Авторизация в панели использует cookie `invoice_session`. При входе и в `auth/me` возвращается `csrf_token`: передавайте его в **X-CSRF-Token** для всех изменяющих запросов, кроме login. В Swagger браузер использует уже открытую cookie-сессию; скопируйте токен из `auth/me` в поле `x-csrf-token` нужной операции. Cookie HttpOnly, SameSite=Strict; CSRF-токены в БД и URL не публикуются. Срок сессии — 12 часов. Смена пароля пользователя и его удаление отзывают все его сессии. Изменение admin-пароля в `.env` после перезапуска отзывает прежние админские сессии.

Примеры тела запроса:

```json
{"title":"Облачный сервер", "amount":"24.00", "currency":"USD", "first_due_date":"2026-10-26", "frequency":"monthly"}
```

```json
{"paid":true, "paid_at":"2026-10-23"}
```

Исправление даты: `{"paid_at":"2026-10-22"}`. Отмена: `{"paid":false}` или `{"paid_at":null}`. Доступные фильтры списка: `from_date`, `to_date`, `status=paid|unpaid|overdue`, `currency=RUB|USD|EUR`, `search`, `include_archived`.

## Проверка

```sh
go test ./...

```

На GitHub то же самое запускает [workflow `tests`](.github/workflows/tests.yml): `gofmt`, `go vet`, тесты с `-race`, запуск собранного бинарника с демоданными, а для панели — проверка типов, переводов и сборка.

Тесты создают временные SQLite-базы и **не читают/не меняют** рабочую базу или VDS; Telegram, MAX, SMTP, webhook и сервер OFAC заменены тестовыми функциями или локальными серверами. `docs/openapi.json` (OpenAPI 3.0.3) — источник правды для API: из него [oapi-codegen](https://github.com/oapi-codegen/oapi-codegen) генерирует маршруты и типы (`go generate ./internal/api`), поэтому операция без обработчика не соберётся, а каждый JSON-ответ в тестах сверяется со спецификацией — расхождение кода и документации роняет тесты. Покрыты роли и API, CSRF, сессии, пользователи, конец месяца и високосный год, история и перезапуск, точные суммы, статусы, немедленное напоминание, отмена, отсутствие дублей, две конкурентные проверки и неоднозначная доставка.

Сценарий живой защиты и соответствие кейсу: [`docs/DEMO.md`](docs/DEMO.md). Архитектура и ограничения: [`docs/ARCHITECTURE.md`](docs/ARCHITECTURE.md).

## Резервная копия

```sh
go run ./cmd/invoice-keeper backup     # или --destination путь
```

Создаётся новый файл в `backups/` через `VACUUM INTO`; копирование согласованно и при запущенном приложении. Скрипт проверяет `integrity_check`, не перезаписывает существующие файлы и не меняет исходную БД. Для восстановления остановите **только Invoice Keeper**, сохраните текущую БД с её WAL/SHM, затем восстановите копию в новый отдельный путь и задайте его в `DATABASE_PATH`. Бэкапы содержат пользовательские данные и хеши: храните их приватно.

## Docker: необязательный отдельный запуск

Эта конфигурация подготовлена для проверки и не запускается автоматически. Никаких SSH-команд, изменений Nginx, firewall, DNS или существующих контейнеров проект не выполняет.

После создания `.env` можно выполнить:

```sh
docker compose up -d --build keeper
```

Адрес по умолчанию: **http://127.0.0.1:18081**. Имя Compose-проекта `invoice-keeper-hackathon`, данные — в отдельном именованном volume. Контейнер работает без root, с доступной для записи только `/data` и временной `/tmp`, лимитами CPU/памяти и логов. Локальная база `data/` не монтируется и диплом не затрагивается. Контейнерная база изначально пустая, демоданные в неё автоматически не копируются. Остановить только приложение: `docker compose stop keeper`.

Не используйте команды удаления volumes для остановки: они удаляют данные. Перед размещением на VDS сначала проверьте свободный порт и ресурсы и сделайте отдельный бэкап. Для публичного доступа нужен существующий HTTPS reverse proxy и `COOKIE_SECURE=true`; конкретная интеграция в сервер требует отдельного выбора домена/маршрута. По умолчанию внешний доступ закрыт привязкой порта к loopback.
