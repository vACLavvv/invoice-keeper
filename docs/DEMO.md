# Сценарий защиты

Подготовьте отдельный локальный запуск по [README](../README.md). После изменения `frontend/` выполните `npm run build` в этой папке и пересоберите Go-приложение: оно отдаёт встроенный статический экспорт. Для показа реальных уведомлений заранее настройте нужный канал и получателя. Отключённый канал и тест с mock API не являются доказательством доставки.

## Подготовка

- Создайте демобазу командой `invoice-keeper bootstrap --demo`. Пароли находятся в локальном `.env`; не показывайте этот файл на экране и не вставляйте его в презентацию.
- Для личного Telegram нужны `TELEGRAM_ENABLED=true`, действующий `TELEGRAM_BOT_TOKEN` и привязанный аккаунт. Общий `TELEGRAM_CHAT_ID` необязателен. В `/account` нажмите «Привязать Telegram» → «Открыть Telegram и привязать», в боте — «Start / Запустить», затем «Проверить привязку» в панели.
- Для email нужны работающий SMTP, `PUBLIC_BASE_URL` и подтверждённый адрес получателя; для webhook — настроенный принимающий сервис. MAX показывайте как живой канал только после отдельной реальной проверки бота и чата.
- Используйте тестовый платёж и безопасный файл чека. Отметка «Оплачено» записывает решение команды и не выполняет банковский перевод.

## Основной показ

1. **Вход и роли.** Без сессии откройте `GET /api/v1/payment-occurrences` — данные закрыты. Войдите на `/` как администратор. В «Аккаунте» покажите контакты и второй фактор: они настраиваются через панель, а логин/пароль администратора задаются только в окружении или `.env`. Через «Команду» этой учётной записью не управляют.
2. **Новый платёж.** Нажмите «Добавить платёж», создайте «Демонстрация · сервер», 24 USD, первый срок завтра, ежемесячный повтор. При настроенном Telegram покажите настоящее напоминание. Создание инициирует проверку сразу; в остальных случаях покажите честное состояние канала в «Журнал → Доставка» (`/activity`).
3. **Оплата из Telegram.** У привязанного аккаунта откройте `/menu` или `/todo`, нажмите «✅ Оплачено» у выбранного периода. Повторное нажатие не меняет дату и не создаёт повторную оплату. В «Журнал → Действия» найдите платёж по названию: видны автор, действие и срок периода. Если Telegram не настроен, выполните оплату в панели и обозначьте, что транспорт не демонстрируется.
4. **Исправление обычным пользователем.** Войдите под демопользователем. Он может отметить оплату, но не создавать/удалять платежи и не управлять командой. Откройте период: «Подтвердить оплату» сохраняет дату, «Сохранить дату» исправляет её, «Отменить оплату» очищает. Для просроченного демопериода сравните оплату сегодня и в день срока: задержка меняется, срок остаётся прежним.
5. **Календарь и план.** В `/calendar` откройте следующий месяц: у платежа отдельный неоплаченный период. Покажите «Итого:» по дням и итог месяца, с отдельными суммами RUB/USD/EUR; на узком экране дневные итоги находятся под списком платежей. В `/budget` объясните «Осталось оплатить»: план по срокам минус отмеченное как оплаченное. Годовой план учитывает график и паузы, не банковский баланс. Чек прикрепляется к выбранному периоду, а не ко всем повторениям.
6. **Удаление и восстановление.** Снова войдите администратором. Откройте оплаченный тестовый период в календаре, нажмите «Удалить платёж…» → «Только этот период» → «Удалить период». Он исчезнет из календаря, истории и итогов. Перезагрузите страницу, затем откройте «История → Удалённые платежи» (`/trash`), найдите название и нажмите «Восстановить», подтвердите. Проверьте прежнюю дату оплаты и чек. Остальные периоды не меняются.
7. **Весь платёж и архив.** При необходимости повторите удаление с выбором «Весь платёж и повторения». Если один период уже был удалён отдельно, восстановление всего платежа его не возвращает: он появится отдельной строкой в `/trash`. Архив — другое действие: в «Регулярных платежах» выберите «Прекратить повторение» (для разового — «В архив») и подтвердите. История и итоги сохранятся, новые периоды и напоминания прекратятся; удаление скрывает запись из отчётов до восстановления.
8. **Журнал и API.** В «Журнал → Действия» примените «Поиск», «С даты»/«По дату», «Пользователь», «Действие». Название и состояние относятся к текущей записи; подпись исходного события не изменяется при переименовании. Покажите проверку целостности и страницы журнала. В `/api/v1/docs` доступны операции и схемы; экспорт — `/api/v1/openapi.json`.
9. **Сохранность.** На локальном экземпляре остановите только процесс Invoice Keeper и запустите его снова. Покажите сохранённые оплаты, журнал и корзину. Не перезапускайте production ради этого сценария.

## API для сверки сценария

Все пути ниже начинаются с `/api/v1`. Изменения через cookie-сессию требуют `Origin` и `X-CSRF-Token`; права администратора проверяет сервер.

| Действие | Метод и путь |
|---|---|
| Создать платёж | `POST /recurring-payments` |
| Отметить/исправить/отменить оплату | `PATCH /payment-occurrences/{id}` |
| Удалить один период | `DELETE /recurring-payments/{id}/periods/{due_date}` |
| Удалить весь платёж | `DELETE /recurring-payments/{id}?mode=delete` |
| Получить корзину | `GET /deleted-payments` |
| Восстановить период | `POST /recurring-payments/{id}/periods/{due_date}/restore` |
| Восстановить весь платёж | `POST /recurring-payments/{id}/restore` |
| Архивировать, сохранив историю в отчётах | `DELETE /recurring-payments/{id}` без `mode=delete` |
| Найти действия по платежу | `GET /audit-log/page?search=...` |
| Проверить подписи журнала | `GET /audit-log/verify` |
| Посмотреть доставки | `GET /reminders`, `GET /deliveries` |
| Получить годовой план | `GET /budget?year=2026` |

## Очередь уведомлений: что доказывать тестами

Личные Telegram-напоминания до срока и о просрочке сохраняются в `deliveries` с каналом `telegram:<chat_id>`. Состояние, число попыток и `retry_after` переживают перезапуск; повтор заведомо недоставленного сообщения ограничен пятью попытками. `sent` и `uncertain` не повторяются автоматически. Перед сетевым вызовом заново проверяются привязка, ответственный и возможность оплаты; отвязка отменяет ожидающую доставку.

Не создавайте таймауты и ошибки в рабочем боте ради показа. Сценарии 429, конкурентных workers, отвязки, смены ответственного, старой очереди и прерванной отправки покрыты `telegram_delivery_test.go`. Тесты показывают логику на контролируемом транспорте; живое сообщение отдельно подтверждает реальную конфигурацию. Строгое exactly-once у Telegram без ключа идемпотентности не гарантируется.
